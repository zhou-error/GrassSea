## 概念讲解

### 什么是中间件（Middleware）？

中间件是介于"网络请求"和"业务逻辑"之间的一层处理逻辑。你可以把它想象成机场安检——每个旅客（请求）在登机（到达业务代码）前，都要经过一系列检查。

```
FastAPI 中间件的"洋葱模型":

    请求进入 ──────────────────────────────▶
              ┌─────────────────────────┐
              │   ① CORS 中间件          │  ← 第一层: 跨域检查
              │  ┌───────────────────┐  │
              │  │ ② JWT 认证中间件    │  │  ← 第二层: 身份验证
              │  │ ┌───────────────┐ │  │
              │  │ │ ③ RBAC 鉴权   │ │  │  ← 第三层: 权限检查
              │  │ │ ┌─────────┐   │ │  │
              │  │ │ │ 业务逻辑 │   │ │  │  ← 核心: 实际处理
              │  │ │ └─────────┘   │ │  │
              │  │ │ ④ 审计日志   │ │  │  ← 第四层: 记录操作
              │  │ └───────────────┘ │  │
              │  └───────────────────┘  │
              │                         │
              └─────────────────────────┘
    响应返回 ◀──────────────────────────────

洋葱模型核心：请求逐层进入，响应逐层退出。
中间件可以"看到"请求和响应，但业务代码只能"看到"请求。
```

### CORS（跨域资源共享）

CORS 解决的是浏览器的同源策略限制。当你的前端（`localhost:5173`）想调用后端 API（`localhost:8000`）时，浏览器会阻止这个"跨域"请求，除非服务器明确说了"允许"。

```
同源策略限制:

  http://localhost:5173  ──请求──▶  http://localhost:8000
       (前端)                          (后端)
              │                              │
              │   端口不同 = 不是同源          │
              │   浏览器阻止请求 ❌            │
              │                              │
              └──── 除非后端设置 CORS 头 ──────┘

CORS 握手过程:

  Step 1: 浏览器发送 "预检请求" (OPTIONS)
  ┌──────────────────────────────────────────┐
  │ OPTIONS /api/data HTTP/1.1               │
  │ Origin: http://localhost:5173            │
  │ Access-Control-Request-Method: POST      │
  └──────────────────────────────────────────┘

  Step 2: 服务器返回 "允许列表"
  ┌──────────────────────────────────────────┐
  │ HTTP/1.1 204 No Content                  │
  │ Access-Control-Allow-Origin: localhost:5173│
  │ Access-Control-Allow-Methods: POST, GET   │
  │ Access-Control-Max-Age: 3600             │
  └──────────────────────────────────────────┘

  Step 3: 浏览器检查通过，发送真正的请求 ✓
```

### HTTP 安全响应头

安全 Headers 是服务器在响应中"告诉浏览器怎么做"的一组指令。它们不防黑客入侵服务器，但能防御常见的 Web 攻击。

```
安全 Header 一览:

X-Content-Type-Options: nosniff
┌──────────────────────────────────────────────┐
│ 防止浏览器 MIME 嗅探                         │
│ 例: 攻击者上传一个 .txt 文件但内容是 <script> │
│     浏览器可能"聪明地"把它当 HTML 执行        │
│     nosniff 告诉浏览器: "不要猜测，严格按     │
│     Content-Type 来"                         │
└──────────────────────────────────────────────┘

X-Frame-Options: DENY
┌──────────────────────────────────────────────┐
│ 防止点击劫持（Clickjacking）                  │
│ 攻击者在自己的页面里用 <iframe> 嵌入你的页面  │
│ 用户以为在点"下载"按钮，实际点了"转账"       │
│ DENY = 禁止任何 iframe 嵌入                   │
└──────────────────────────────────────────────┘

X-XSS-Protection: 1; mode=block
┌──────────────────────────────────────────────┐
│ 启用浏览器内置的 XSS 过滤器                   │
│ 当检测到疑似 XSS 攻击时，阻止页面加载         │
└──────────────────────────────────────────────┘

Strict-Transport-Security: max-age=31536000
┌──────────────────────────────────────────────┐
│ HSTS: 强制浏览器使用 HTTPS                    │
│ max-age 单位是秒，31536000 = 1年             │
│ 一旦浏览器收到这个头，1年内对该域名只走 HTTPS │
│ 防止中间人将 HTTPS 降级为 HTTP                │
└──────────────────────────────────────────────┘

Content-Security-Policy: ...
┌──────────────────────────────────────────────┐
│ CSP: 内容安全策略，限制页面可以加载哪些资源    │
│ default-src 'self' = 只加载来自本站的资源    │
│ script-src 'self' = 脚本只从本站加载          │
│ img-src 'self' data: blob:                   │
│   = 图片可以从本站、data URI 和 blob URI 加载 │
└──────────────────────────────────────────────┘
```

## 项目代码精讲

### CORS 中间件配置

```python
# shared/middleware/security.py 第101-110行
def setup_security(app: FastAPI) -> None:
    """配置安全中间件"""
    app.add_middleware(
        CORSMiddleware,
        allow_origins=["http://localhost:3000", "http://localhost:5173"],
        allow_credentials=True,
        allow_methods=["GET", "POST", "PUT", "DELETE", "PATCH"],
        allow_headers=["*"],
        max_age=3600,
    )
```

**逐段解析**：

1. `allow_origins=[...]` — 白名单，只允许这两个来源的跨域请求。这是安全关键配置——不要使用 `["*"]`（允许所有来源），因为那会让任意网站都能调用你的 API。

2. `allow_credentials=True` — 允许携带 Cookie 和 Authorization 头。如果前端使用 JWT Token，必须设置为 `True`。

3. `allow_methods=[...]` — 允许的 HTTP 方法。这里包括了 RESTful API 常用的五种方法。

4. `allow_headers=["*"]` — 允许所有请求头。`"*"` 在这里是合理的设计，因为 API 客户端可能携带各种自定义头（如 `X-API-Key`、`X-Trace-Id`）。

5. `max_age=3600` — 预检请求的缓存时间（单位：秒）。3600 秒 = 1 小时。在这段时间内，同一个来源的后续请求不需要再次发预检请求，提升了性能。

### SecurityHeadersMiddleware 类

```python
# shared/middleware/security.py 第88-98行
class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    """安全 Header — CSP, XSS Protection, HSTS"""

    async def dispatch(self, request: Request, call_next):
        response = await call_next(request)
        response.headers["X-Content-Type-Options"] = "nosniff"
        response.headers["X-Frame-Options"] = "DENY"
        response.headers["X-XSS-Protection"] = "1; mode=block"
        response.headers["Strict-Transport-Security"] = \
            "max-age=31536000; includeSubDomains"
        response.headers["Content-Security-Policy"] = \
            "default-src 'self'; script-src 'self' 'unsafe-inline'; " \
            "style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:"
        return response
```

**逐段解析**：

1. `class SecurityHeadersMiddleware(BaseHTTPMiddleware)` — 继承 Starlette 的 `BaseHTTPMiddleware`。这是 FastAPI/Starlette 框架提供的基类，只需要实现 `dispatch` 方法即可。

2. `async def dispatch(self, request, call_next)` — 中间件的入口方法。`call_next` 是一个回调函数，调用它会把请求传递到下一个中间件（或最终的业务代码）。

3. `response = await call_next(request)` — **洋葱模型的核心**。这一行之前：请求进入；这一行之后：响应返回。我们在这里拦截响应，给它加上安全头。

4. 五个安全头一行行添加。每个头的含义已在"概念讲解"中详述。注意 CSP 策略中 `'unsafe-inline'` 是一个折中——完全禁用内联脚本最安全，但前端框架（React/Vue）通常需要内联样式，所以在开发阶段放开了这个限制。

### AuditMiddleware 审计日志

```python
# shared/middleware/security.py 第68-83行
class AuditMiddleware(BaseHTTPMiddleware):
    """审计日志 — 记录所有操作到 TimescaleDB"""

    async def dispatch(self, request: Request, call_next):
        response = await call_next(request)

        logger.info(
            "audit_log",
            method=request.method,
            path=request.url.path,
            status=response.status_code,
            ip=request.client.host if request.client else "unknown",
            user_agent=request.headers.get("User-Agent", ""),
        )

        return response
```

**逐段解析**：

1. 和 `SecurityHeadersMiddleware` 一样，继承 `BaseHTTPMiddleware`。

2. `response = await call_next(request)` — 先执行后续的中间件和业务逻辑，拿到响应后再记录。

3. `logger.info("audit_log", ...)` — 使用结构化日志记录关键信息：
   - `method`: HTTP 方法（GET/POST/PUT/DELETE）
   - `path`: 请求路径（如 `/rag/query`）
   - `status`: 响应状态码（200/401/500 等）
   - `ip`: 客户端 IP 地址
   - `user_agent`: 浏览器/客户端标识

4. `request.client.host if request.client else "unknown"` — 防御性编程。在某些代理配置下 `request.client` 可能为 `None`，直接访问 `.host` 会抛出 AttributeError。这里用三元表达式做了安全处理。

审计日志的价值在于：
- **事后追溯**：出了问题能查到"谁在什么时间做了什么操作"
- **异常检测**：通过分析日志发现异常模式（如短时间内大量 401 响应）
- **合规要求**：某些行业要求保留完整的操作审计记录

### 中间件的注册顺序

```python
# 第101-113行
def setup_security(app: FastAPI) -> None:
    app.add_middleware(CORSMiddleware, ...)       # 第一层
    app.add_middleware(SecurityHeadersMiddleware)  # 第二层
    app.add_middleware(AuditMiddleware)            # 第三层
```

**顺序很重要**：CORS 中间件必须在最外层，因为如果跨域检查失败，后续的安全头和审计都无意义（请求会被浏览器直接拦截）。

## 常见问题与排错

**Q1：为什么 `.env` 中的 `APP_ENV=production` 时 CSP 策略应更严格？**

A：开发阶段为了方便调试，CSP 中允许 `'unsafe-inline'`（内联脚本/样式）。生产环境应去除这些宽松策略，改用 nonce 或 hash-based CSP，这样即使被 XSS 注入了 `<script>` 标签也无法执行。GrassSea 当前 CSP 是开发阶段的配置。

**Q2：审计日志会拖慢性能吗？**

A：GrassSea 使用异步日志框架 structlog，日志写入是异步的，对请求响应时间影响极小（通常 < 1ms）。但如果日志量极大（每秒上千条），建议使用消息队列（如 RabbitMQ）缓冲后批量写入。

**Q3：CORS 的 `allow_origins=["*"]` 和 `allow_credentials=True` 能一起用吗？**

A：不能。浏览器安全策略规定：如果 `allow_credentials=True`，`allow_origins` 不能是 `"*"`，必须指定具体的域名。这是为了防止恶意网站窃取用户的认证凭证。
