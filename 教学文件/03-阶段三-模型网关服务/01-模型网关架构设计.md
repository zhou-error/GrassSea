## 概念讲解

### 一、问题：直接调用 LLM 有什么不好？

假设没有模型网关，每个服务直接调用 LLM：

```
agent_service ──────────────> DeepSeek API
    │
knowledge_service ──────────> DeepSeek API
    │
chat_service ───────────────> DeepSeek API
    │
... 其他 5 个服务 ──────────> DeepSeek API
```

这种架构的问题：

**问题 1：配置分散**。DeepSeek 的 API Key 需要在 8 个服务中配置。如果更换 Key，需要改 8 处。

**问题 2：切换模型困难**。想从 DeepSeek 切换到 Claude？需要改所有调用代码。

**问题 3：缺少统一监控**。谁调了多少 Token？哪个服务调用最多？无法集中统计。

**问题 4：重复造轮子**。每个服务都要写一遍：构造请求、解析响应、处理流式输出、错误重试……

### 二、模型网关的解决方案

```
BEFORE (没有网关):                          AFTER (有网关):

agent ──> DeepSeek                         agent ──┐
knowledge ──> DeepSeek                      knowledge ──┤
chat ──> DeepSeek                           chat ──┤
cad ──> Claude                              cad ──┤
review ──> DeepSeek                          review ──┤
                                            所有服务 ──> 模型网关 ──> DeepSeek
                                                               ──> Claude
                                        统一入口               ──> GPT
                                        统一管理
                                        统一监控
```

```
┌──────────────────────────────────────────────────┐
│                  Model Gateway                    │
│                                                  │
│  ┌────────────────────────────────────────────┐  │
│  │          /v1/chat/completions               │  │
│  │        (OpenAI 兼容接口)                     │  │
│  └────────────────────────────────────────────┘  │
│                      │                           │
│         ┌────────────┼────────────┐              │
│         v            v            v              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐         │
│  │  Router  │ │  SSE     │ │  Token   │         │
│  │ 多模型路由 │ │ 流式输出  │ │ 统计追踪  │         │
│  └──────────┘ └──────────┘ └──────────┘         │
│         │                                        │
│    ┌────┴────┐                                   │
│    v         v                                   │
│  DeepSeek  Claude                                │
│  (OpenAI   (Anthropic                            │
│   兼容)     API)                                  │
└──────────────────────────────────────────────────┘
```

**网关的三大职责**：

| 职责 | 实现 | 价值 |
|------|------|------|
| 统一入口 | `/v1/chat/completions` 端点 | 所有服务调同一个接口 |
| 智能路由 | `ModelRouter` | 按任务类型/成本/延迟自动选模型 |
| 追踪统计 | `TokenTracker` | 统一 Token 用量和延迟统计 |

### 三、OpenAI 兼容接口

OpenAI 的 `/v1/chat/completions` 已经成为 LLM API 的事实标准。绝大多数模型提供商（DeepSeek、通义千问、智谱等）都兼容这个接口格式。

```
OpenAI /v1/chat/completions 格式:

请求:
{
  "model": "gpt-4",
  "messages": [
    {"role": "system", "content": "你是助手"},
    {"role": "user", "content": "你好"}
  ],
  "stream": false,
  "temperature": 0.7,
  "max_tokens": 4096
}

响应:
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion",
  "created": 1234567890,
  "model": "gpt-4",
  "choices": [{
    "index": 0,
    "message": {"role": "assistant", "content": "你好！"},
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 5,
    "total_tokens": 15
  }
}
```

**GrassSea 的策略**：模型网关对外提供 OpenAI 兼容接口，对内适配不同提供商的 API 格式。这样：

1. 业务代码只需要知道 OpenAI 格式（一种格式）
2. 网关负责转换（DeepSeek 的格式 → OpenAI 格式，Claude 的格式 → OpenAI 格式）
3. 切换模型对业务代码完全透明


### main.py —— 应用入口

#### 生命周期管理

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    global model_router, token_tracker
    setup_logging(level="DEBUG" if settings.APP_DEBUG else "INFO")
    logger.info("Model Gateway starting...")

    model_router = ModelRouter(settings)
    await model_router.initialize()

    token_tracker = TokenTracker()

    logger.info("Model Gateway started", port=settings.MODEL_GATEWAY_PORT)
    yield

    logger.info("Model Gateway shutting down...")
    if model_router:
        await model_router.close()
```

生命周期分为三个阶段：

```
启动 (yield 之前):
1. 初始化日志
2. 创建 ModelRouter 实例
3. 调用 initialize() 建立 HTTP 客户端 + 注册模型
4. 创建 TokenTracker 实例

运行 (yield):
5. 处理 HTTP 请求

关闭 (yield 之后):
6. 关闭 HTTP 客户端连接
```

#### 配置热加载端点

```python
@app.post("/admin/reload")
async def reload_config(config: dict[str, str]):
    """运行时重载模型配置，无需重启容器"""
    global model_router

    # 更新 settings 和环境变量
    for key, value in config.items():
        if hasattr(settings, key):
            setattr(settings, key, value)
            os.environ[key] = value

    # 重新初始化模型路由器
    if model_router:
        await model_router.close()
    model_router = ModelRouter(settings)
    await model_router.initialize()
```

这是生产环境非常有用的功能——换了 API Key 不需要重启服务。

### Pydantic 请求/响应模型

```python
class ChatMessage(BaseModel):
    role: str = "user"            # system / user / assistant
    content: str

class ChatCompletionRequest(BaseModel):
    model: str = "deepseek-chat"
    messages: list[ChatMessage]
    stream: bool = False           # 是否流式输出
    temperature: float = Field(default=0.7, ge=0.0, le=2.0)
    max_tokens: int = Field(default=4096, ge=1, le=128000)
    top_p: float = Field(default=1.0, ge=0.0, le=1.0)
    user: Optional[str] = None     # 用于追踪的用户标识
```

`Field()` 的参数含义：
- `ge`（greater than or equal）：最小值
- `le`（less than or equal）：最大值

例如 `temperature: float = Field(default=0.7, ge=0.0, le=2.0)` 表示：
- 默认值 0.7
- 最小值 0.0
- 最大值 2.0
- 超出范围时自动返回 422 错误

## 常见问题与排错

### Q1: 为什么模型网关自己也是一个独立服务？
解耦。网关可以独立扩缩容、独立升级、独立配置。如果网关逻辑内嵌在 chat_service 中，每次修改路由策略都要重启整个 chat_service。

### Q2: 网关会不会成为性能瓶颈？
会。网关是所有 LLM 调用的必经之路。优化策略：
- 使用 httpx 异步客户端（非阻塞 I/O）
- 连接池复用（`max_keepalive_connections=10`）
- 流式转发（不缓存完整响应）
- 水平扩展（多实例 + 负载均衡）

### Q3: 如何处理 LLM API 的速率限制（Rate Limit）？
模型网关可以内置重试和退避逻辑：
```python
# 指数退避重试
for attempt in range(3):
    try:
        return await call_llm()
    except RateLimitError:
        await asyncio.sleep(2 ** attempt)  # 1s, 2s, 4s
```

### Q4: 为什么要暴露 OpenAI 兼容接口？
让任何使用 OpenAI SDK 的代码可以无缝切换到 GrassSea。无论是 LangChain、LlamaIndex 还是其他工具，都可以直接通过 OpenAI SDK 调用 GrassSea 的模型网关。
