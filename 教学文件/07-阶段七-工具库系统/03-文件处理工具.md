# 03 - 文件处理工具

## 学习目标

1. 理解 GrassSea 中五个文件处理工具的设计模式：表格解析、PDF解析、OCR识别、联网搜索、待办管理
2. 掌握工具 Manifest 设计时 `category` 选型的原则
3. 理解 `SEARCH` 类别与 `FILE` 类别的区别
4. 学会如何为文件处理类工具设计输入输出 schema

## 前置知识

- 掌握 `BaseTool` 和 `ToolManifest` 的基本用法（参见上一节）
- 了解 JSON Schema 的 `"type": "string"` 和 `"type": "integer"` 类型
- 不需要了解 PyMuPDF、PaddleOCR 等库的具体API（本节仅讲解工具层设计）

## 概念讲解

### 五个文件处理工具概览

```
        +--------------------------------------------------+
        |          文件处理工具群 (FILE + SEARCH)            |
        |                                                  |
        |  XlsxParserTool     — 表格解析 (xlsx/xls/csv)    |
        |  PdfParserTool      — PDF解析 (文本/表格提取)     |
        |  OcrEngineTool      — OCR识别 (图纸标注识别)      |
        |  WebSearchTool      — 联网搜索 (Brave/Bing API)  |
        |  TodoManagerTool    — 待办管理 (创建/更新/提醒)   |
        +--------------------------------------------------+
```

这五个工具覆盖了船舶工程师日常工作的文件处理需求：
- 从 Excel 型值表中提取数据
- 从 PDF 规范文件中提取条文
- 从扫描图纸中识别标注文字
- 联网搜索最新规范和技术文献
- 管理设计任务和待办事项

### 工具分类设计思想

注意看四个工具用的是 `ToolCategory.FILE`，但 WebSearchTool 用的是 `ToolCategory.SEARCH`。为什么？

```
FILE = "file"       -> 处理实体文件（上传、解析、转换）
SEARCH = "search"   -> 获取外部信息（搜索、检索）
```

这个分类让注册中心的 `list_tools(category=ToolCategory.FILE)` 可以精确筛选出"文件处理"相关工具列表，方便前端按类别展示。

### Manifest 设计对比

| 工具 | 类别 | 超时 | 鉴权 | 限频 |
|------|------|------|------|------|
| XlsxParser | FILE | 30s | 否 | 60 |
| PdfParser | FILE | 60s | 否 | 60 |
| OCR Engine | FILE | 60s | 否 | 60 |
| WebSearch | SEARCH | 15s | 否 | 60 |
| TodoManager | FILE | 10s | 否 | 60 |

几个值得注意的差异：
- **PDF解析超时 60s** — 大型规范文件可能几百页，解析需要时间
- **OCR 超时 60s** — 图像识别计算量大
- **联网搜索仅 15s** — 外部 API 通常秒级响应，太长反而不合理
- **待办管理仅 10s** — 数据库操作很快

## 项目代码精讲

### 1. XlsxParserTool — 表格解析

**文件位置**: `tools/file/xlsx_parser.py`

```python
XLSX_PARSER_MANIFEST = ToolManifest(
    tool_id="xlsx_parser",
    name="表格解析",
    description="型值表结构化提取，支持 xlsx/xls/csv",
    category=ToolCategory.FILE,
    input_schema={
        "type": "object",
        "properties": {
            "file_path": {"type": "string"},
            "sheet_name": {"type": "string"}
        }
    },
    output_schema={
        "type": "object",
        "properties": {
            "headers": {"type": "array"},
            "rows": {"type": "integer"},
            "data": {"type": "array"}
        }
    },
)
```

**代码精讲**：

输入参数只有两个字段：`file_path`（文件路径）和 `sheet_name`（工作表名）。`sheet_name` 是可选参数，因为 `openpyxl` 库本身有默认值。

输出 schema 声明了三个字段：
- `headers`: 列名数组（如 `["站号", "半宽", "吃水"]`）
- `rows`: 总行数
- `data`: 结构化数据数组

```python
class XlsxParserTool(BaseTool):
    def __init__(self): super().__init__(XLSX_PARSER_MANIFEST)

    async def execute(self, params: dict, context: dict) -> dict:
        return {
            "status": "completed",
            "file": params.get("file_path", ""),
            "sheet": params.get("sheet_name", "Sheet1"),
            "headers": ["站号", "半宽", "吃水", "纵剖线高"],
            "rows": 21,
            "data_sample": [
                {"station": i, "half_breadth": 5.0 + i * 0.3,
                 "draft": 4.0 + i * 0.05}
                for i in range(5)
            ],
        }
```

注意这里返回的是 `data_sample`（样例数据），而非完整数据。这是因为教学阶段的工具使用"模拟数据"——在实际开发中，`execute` 方法会用 `openpyxl` 库真正读取文件。

### 2. PdfParserTool — PDF 解析

**文件位置**: `tools/file/pdf_parser.py`

```python
PDF_PARSER_MANIFEST = ToolManifest(
    tool_id="pdf_parser",
    name="PDF 解析",
    description="规范文件文本/表格提取，支持 PyMuPDF/pdfplumber",
    ...
    input_schema={
        "type": "object",
        "properties": {
            "file_path": {"type": "string"},
            "pages": {"type": "string"}  # 页码范围，如 "1-10"
        }
    },
    timeout_ms=60000,  # 大文件需要更长时间
)
```

`pages` 参数的类型是 `"string"` 而不是 `"integer"`，因为页码范围可能用 `"1-10,15,20-30"` 这样的格式。这种设计考虑了实际使用场景——用户可能只需要解析文件中的某几页。

**输出结构的设计思考**：

```python
return {
    "status": "completed",
    "file": params.get("file_path", ""),
    "pages": 20,
    "text_preview": "规范条文内容摘要...",
    "tables_extracted": 3,
    "sections": ["第1章 总则", "第2章 船体结构", "第3章 稳性"],
}
```

- `text_preview` — 文本预览（前几百字），让调用方快速了解内容
- `tables_extracted` — 提取到的表格数量，方便判断解析效果
- `sections` — 法规/规范通常有清晰的章节结构，返回章节列表非常实用

### 3. OcrEngineTool — 图纸 OCR

**文件位置**: `tools/file/ocr_engine.py`

```python
OCR_ENGINE_MANIFEST = ToolManifest(
    tool_id="ocr_engine",
    name="图纸 OCR",
    description="扫描图纸文字/标注识别，支持 PaddleOCR/Tesseract",
    ...
    input_schema={
        "type": "object",
        "properties": {
            "image_path": {"type": "string"},
            "language": {"type": "string"}  # 如 "chi_sim+eng"
        }
    },
)
```

`language` 参数很有讲究。船舶图纸可能混合中文和英文标注，所以默认值 `"chi_sim+eng"` 同时识别简体中文和英文。

**输出结构**：

```python
"text_boxes": [
    {
        "text": "型线图",
        "bbox": [100, 50, 200, 80],  # [x1, y1, x2, y2]
        "confidence": 0.98
    }
],
"overall_confidence": 0.95,
```

每个识别结果包含：
- `text` — 识别的文字内容
- `bbox` — 文字框的边界坐标（在图像中的位置）
- `confidence` — 识别置信度（0-1）

`bbox` 数组 [x1, y1, x2, y2] 的格式是 OCR 领域的事实标准——左上角 (x1, y1) 和右下角 (x2, y2)。

`overall_confidence` 是整体置信度，可以用来判断识别效果。如果置信度过低（< 0.7），调用方可以选择让用户人工复核。

### 4. WebSearchTool — 联网搜索

**文件位置**: `tools/file/web_search.py`

```python
WEB_SEARCH_MANIFEST = ToolManifest(
    tool_id="web_search",
    name="联网搜索",
    description="联网搜索补充最新信息，支持 Brave Search / Bing API",
    category=ToolCategory.SEARCH,  # 注意：和上面4个不同！
    input_schema={
        "type": "object",
        "properties": {
            "query": {"type": "string"},
            "num_results": {"type": "integer"}
        }
    },
    timeout_ms=15000,  # 15秒 — 外部API调用应设短超时
)
```

这个工具的 `category` 是 `ToolCategory.SEARCH`，和其他四个工具不同。为什么这样设计？因为"联网搜索"的本质是从外部获取信息，而不是处理用户上传的文件。分类的目的就是让注册中心可以精确筛选。

**返回结果设计**：

```python
return {
    "status": "completed",
    "query": query,
    "results": [
        {
            "title": f"关于 '{query[:30]}' 的搜索结果",
            "url": "https://example.com",
            "snippet": "相关内容摘要..."
        }
    ],
    "total": 1,
    "engine": "Brave Search",
}
```

- `query` — 原样返回搜索关键词（方便前端展示 "搜索 ${query}"）
- `engine` — 标明使用的搜索引擎，方便调试
- `results` — 搜索结果数组，每条包含标题、URL和摘要

### 5. TodoManagerTool — 待办管理

**文件位置**: `tools/file/todo_manager.py`

```python
TODO_MANAGER_MANIFEST = ToolManifest(
    tool_id="todo_manager",
    name="待办管理",
    description="创建/更新/提醒待办事项，与 PostgreSQL 同步",
    category=ToolCategory.FILE,
    input_schema={
        "type": "object",
        "properties": {
            "action": {"type": "string"},   # "create" / "update" / "delete"
            "title": {"type": "string"},
            "priority": {"type": "string"}  # "high" / "medium" / "low"
        }
    },
    timeout_ms=10000,  # 数据库操作很快
)
```

这个工具的 `action` 参数设计了一种"操作路由"模式——通过 `action` 字段区分不同的业务操作，而不是为每种操作创建单独的工具。这是一种常见的 API 设计模式，当你有一组相关操作时，用一个字段来路由比创建 N 个独立工具更清晰。

**哈希生成 ID**：

```python
"todo_id": f"todo_{hash(params.get('title', '')) % 100000}",
```

`hash()` 是 Python 内置函数，`% 100000` 取模保证 ID 在合理范围内。这是快速生成伪唯一 ID 的简单方法。

from tools.file.pdf_parser import PdfParserTool

async def main():

### 实践2: 对比 FILE 和 SEARCH 类的工具

```python
from tools.file.pdf_parser import PDF_PARSER_MANIFEST
from tools.file.web_search import WEB_SEARCH_MANIFEST

# 对比两个 manifest 的配置差异
manifests = {"PDF解析": PDF_PARSER_MANIFEST, "联网搜索": WEB_SEARCH_MANIFEST}

for name, m in manifests.items():
    print(f"{name}:")
    print(f"  类别: {m.category}")
    print(f"  超时: {m.timeout_ms}ms")
    print(f"  鉴权: {m.requires_auth}")
    print(f"  限频: {m.rate_limit_per_min}/min")
    print()
```

你可能会发现 PDF 解析的超时是搜索的4倍——思考一下为什么？答案：PDF 解析需要逐页读取、富文本提取、表格识别，而搜索只需一次 HTTP 请求。

### 实践3: 编写一个简单的文件工具

仿照 `XlsxParserTool`，编写一个 `CsvParserTool`：

```python
CSV_MANIFEST = ToolManifest(
    tool_id="csv_parser",
    name="CSV 解析",
    description="CSV 文件结构化提取",
    category=ToolCategory.FILE,
    input_schema={
        "type": "object",
        "properties": {
            "file_path": {"type": "string"},
            "delimiter": {"type": "string"}
        }
    },
    output_schema={
        "type": "object",
        "properties": {
            "headers": {"type": "array"},
            "rows": {"type": "integer"}
        }
    },
)

class CsvParserTool(BaseTool):
    def __init__(self): super().__init__(CSV_MANIFEST)

    async def execute(self, params: dict, context: dict) -> dict:
        return {
            "status": "completed",
            "headers": ["col1", "col2", "col3"],
            "rows": 100,
            "delimiter": params.get("delimiter", ","),
        }
```

## 常见问题与排错

### Q1: 为什么工具返回的是模拟数据而不是真实数据？

当前教学阶段的工具使用"模拟数据"（mock data），目的是让你先理解工具的协议设计和数据结构。真实实现需要引入具体库（如 openpyxl / PyMuPDF / PaddleOCR），这些会在后续开发中逐步接入。这也是"协议先行"开发模式的体现——先定义好接口规范，再逐步实现。

### Q2: 联网搜索工具的 API Key 在哪配置？

API Key 存储在 GrassSea 的加密配置系统（`shared/utils/secrets.py`）中，通过 Chat Service 的配置管理 API 设置，服务启动时自动解密并注入环境变量。具体机制参见"配置管理API"章节。

### Q3: OCR 的 `confidence` 字段有什么用途？

可以用于"低置信度结果人工复核"的场景。例如：
- confidence > 0.95: 自动采纳
- 0.8 < confidence < 0.95: 标注"待确认"
- confidence < 0.8: 提示用户人工复核

### Q4: `todo_id` 用 hash 生成会不会重复？

`hash() % 100000` 在小规模使用中重复概率极低。在实际项目中，如果并发创建待办事项，建议使用 UUID 生成器（`uuid.uuid4()`），它几乎是"数学上保证不重复"的。
