## 概念讲解

### 一、什么是 Monorepo

Monorepo 是"Monolithic Repository"的缩写，中文叫"单体仓库"或"单仓"。它的核心思想很简单：**把整个项目的所有代码放在一个 Git 仓库里，而不是拆成多个小仓库。**

```
传统 Multi-Repo 模式:          Monorepo 模式:

  repo-frontend/                 grasssea/
  repo-backend/                  ├── frontend/      (前端)
  repo-shared/                   ├── services/      (后端服务)
  repo-agents/                   ├── agents/        (智能体)
  repo-tools/                    ├── tools/         (工具库)
  共 5 个仓库                     ├── shared/        (共享库)
                                 └── docs/          (文档)
                                 共 1 个仓库
```

**Monorepo 的优点**（也是 GrassSea 选择它的原因）：

1. **代码共享方便** — `shared/` 目录下的代码可以被所有服务直接引用，不需要发布成 pip 包
2. **统一版本管理** — 一次 `git checkout` 就能获得整个项目的完整状态
3. **原子性提交** — 一个功能可能同时修改前端和后端，一个 commit 搞定
4. **统一工具链** — 所有子项目共用同一套 lint、format、test 配置

**Monorepo 的挑战**：
- 仓库体积会变大（但 Git 对代码仓库处理得很好）
- 需要更清晰的目录约定，否则会混乱

### 二、GrassSea 的五层架构

GrassSea 采用分层架构设计，从上到下共五层。理解这个架构是读懂整个代码库的关键。

```
┌──────────────────────────────────────────────────────────┐
│                  多端交互层 (Presentation)                 │
│   React 18 SPA  │  API Gateway  │  WebSocket            │
├──────────────────────────────────────────────────────────┤
│                 智能体编排层 (Orchestration)               │
│   意图识别  │  任务规划(DAG)  │  会话状态机  │  多智能体协同  │
├──────────────────────────────────────────────────────────┤
│                 业务智能体层 (Business Agents)             │
│   PM Agent  │  船舶工程师  │  CAD Agent  │  审查  │  研究员  │
├──────────────────────────────────────────────────────────┤
│                   能力中台层 (Capability)                  │
│   RAG 引擎  │  知识图谱  │  模型网关  │  仿真引擎  │  工具库  │
├──────────────────────────────────────────────────────────┤
│                   数据底座层 (Data Infrastructure)         │
│   PostgreSQL  │  MongoDB  │  Milvus  │  Redis  │  MinIO  │
└──────────────────────────────────────────────────────────┘
```

**每一层在代码目录中的体现**：

| 层级 | 目录 | 说明 |
|------|------|------|
| 多端交互层 | `frontend/` + `services/chat_service/` | 用户看到的界面 + API 入口 |
| 智能体编排层 | `services/agent_service/` | 大脑——决定"谁来做、怎么做" |
| 业务智能体层 | `agents/` | 专家——每个 Agent 精通一个领域 |
| 能力中台层 | `services/knowledge_service/` + `services/model_gateway/` + `tools/` | 工具箱——提供 AI 和计算能力 |
| 数据底座层 | `shared/models/` + `docker-compose.yml` | 存储——所有数据的家 |

**数据流动路径**（一个典型的用户请求）：

```
用户浏览器 ──HTTP──> chat_service (API网关)
                        │
                        v
                   agent_service (编排层: 意图识别→任务规划)
                        │
                   ┌────┼────┐
                   v    v    v
               Agent  Agent  Agent  (业务智能体)
                 │      │      │
                 v      v      v
           model_gateway  knowledge_service  tools
           (调用LLM)      (RAG检索)         (计算)
                 │      │      │
                 v      v      v
           PostgreSQL  MongoDB  Milvus  Redis
```

### 三、Python 包的组织方式

#### `__init__.py` 的作用

在 Python 中，一个目录要成为"包"（package），必须包含一个 `__init__.py` 文件（Python 3.3+ 中隐式命名空间包除外）。这个文件有两个核心作用：

1. **标识**：告诉 Python 解释器"这个目录是一个包"
2. **初始化**：定义包的公开接口，控制 `from package import *` 的行为

看看 GrassSea 中 `shared/models/postgres/__init__.py` 的实际代码：

```python
# GrassSea AI — PostgreSQL 数据模型
from shared.models.postgres.base import Base

from shared.models.postgres.project import Project, project_members
from shared.models.postgres.task import TaskRecord
from shared.models.postgres.offset_table import OffsetTable
from shared.models.postgres.todo import TodoItem
from shared.models.postgres.system_config import SystemConfig
from shared.models.postgres.prompt_template import PromptTemplate

__all__ = [
    "Base",
    "Project",
    "project_members",
    "TaskRecord",
    "OffsetTable",
    "TodoItem",
    "SystemConfig",
    "PromptTemplate",
]
```

这样做的好处是：其他模块只需要 `from shared.models.postgres import Project`，而不需要知道 `Project` 定义在 `project.py` 里。这叫**统一出口模式**。

#### 绝对导入 vs 相对导入

```python
# 绝对导入（推荐）—— 从项目根目录出发，路径清晰
from shared.utils.config import get_settings
from shared.models.database import Base

# 相对导入 —— 使用 . 表示当前包，.. 表示上级包
from .config import get_settings      # 同目录
from ..models.database import Base    # 上一级目录
from ...tools.base import ToolBase    # 上两级目录
```

**GrassSea 使用绝对导入**。原因：
- 路径一目了然，新人容易理解
- 重构时 IDE 能自动追踪引用
- 避免"从哪开始算"的困惑

#### setuptools 的包发现机制

在 `pyproject.toml` 中配置：

```toml
[tool.setuptools.packages.find]
where = ["."]
include = ["shared*", "services*", "agents*", "tools*", "scripts*"]
```

这告诉 setuptools："在项目根目录下，把所有以 `shared`、`services`、`agents`、`tools`、`scripts` 开头的目录都当成包来安装"。

## 项目代码精讲

### 核心目录逐一解析

我们按"从底层到上层"的顺序来看 GrassSea 的每个目录：

#### `shared/` — 共享库（被所有服务引用）

```
shared/
├── models/                  # 数据模型
│   ├── database.py          #   数据库连接管理（PG/Mongo/Redis/Milvus）
│   ├── postgres/            #   PostgreSQL 表定义（7 张表）
│   ├── mongodb/             #   MongoDB 集合定义（6 个集合）
│   ├── timescale/           #   TimescaleDB 超表定义（4 张超表）
│   ├── repository/          #   数据访问层（CRUD 封装）
│   └── alembic/             #   数据库迁移工具
├── protocols/               # 接口协议（Agent/Tool 的抽象基类）
├── middleware/               # 中间件（安全/可观测性）
└── utils/                    # 工具模块
    ├── config.py             #   全局配置（pydantic-settings）
    └── logging.py            #   结构化日志（structlog）
```

`shared/` 是整个项目最核心的代码。它定义了所有数据结构和通用能力，但不包含任何业务逻辑。**所有服务都依赖它，但它不依赖任何服务。**

#### `services/` — 后端微服务（每个服务独立运行）

```
services/
├── chat_service/           # API 网关 + 认证（JWT 登录）
├── agent_service/          # 智能体编排（意图识别/任务规划/状态机）
├── knowledge_service/      # RAG 引擎（文档处理/向量检索/答案生成）
├── model_gateway/          # 模型网关（多模型路由/Token统计/流式输出）
└── (预留服务)              # simulation/tool/report/stats
```

每个服务都是独立的 FastAPI 应用，可以单独启动和部署。它们之间通过 HTTP 调用或消息队列（RabbitMQ）通信。

#### `agents/` — 业务智能体

```
agents/
├── base/                   # Agent 基类（所有 Agent 的父类）
├── pm_agent/               # 项目经理 Agent
├── naval_arch_agent/       # 船舶工程师 Agent
├── cad_agent/              # CAD Agent
├── review_agent/           # 审查 Agent
├── research_agent/         # 研究员 Agent
└── doc_agent/              # 文档 Agent
```

每个 Agent 是一个"虚拟员工"，有自己的专业领域和工具。编排层会根据用户意图选择合适的 Agent 来完成任务。

#### `tools/` — 工具库（被 Agent 调用）

```
tools/
├── base/                   # 工具基类 + 注册中心（热插拔机制）
├── compliance/             # 规范审查工具
├── computation/            # 船舶计算工具（静水力/稳性/阻力/船型改造）
├── cad/                    # CAD 工具（绘图/解析/格式转换）
├── file/                   # 文件处理工具（Excel/PDF/OCR/搜索/待办）
└── report/                 # 报告生成工具
```

工具是 Agent 的"手"。Agent 通过调用工具来完成具体操作：计算稳性、解析图纸、搜索文献等。

#### `frontend/` — Web 前端

```
frontend/src/
├── components/             # 通用组件（导航栏/侧边栏/进度条）
├── pages/                  # 页面（登录/对话/知识库/任务中心/设置）
├── stores/                 # 状态管理（Zustand）
└── api/                    # API 客户端（Axios）
```

前端使用 React 18 + TypeScript + Ant Design，通过 HTTP 和 WebSocket 与后端通信。

#### `infrastructure/` — 基础设施配置

```
infrastructure/
├── docker/                 # Dockerfile + 初始化脚本
├── （K3s 部署清单已移除，不在本项目范围）
└── nginx/                  # Nginx 配置（反向代理）
```

## 手把手实践

### 任务：创建一个微型 Monorepo

让我们模拟 GrassSea 的结构，创建一个简单的项目。

**步骤 1**：创建目录结构
```bash
mkdir -p my_project/shared/utils
mkdir -p my_project/services/api_service
mkdir -p my_project/agents/my_agent
mkdir -p my_project/tools/my_tool
```

**步骤 2**：创建 `shared/utils/config.py`（配置模块）
```python
# shared/utils/config.py
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    APP_NAME: str = "MyProject"
    APP_DEBUG: bool = True

    class Config:
        env_file = ".env"

from functools import lru_cache

@lru_cache
def get_settings():
    return Settings()
```

**步骤 3**：创建 `services/api_service/main.py`（FastAPI 服务）
```python
# services/api_service/main.py
from fastapi import FastAPI
from shared.utils.config import get_settings

settings = get_settings()
app = FastAPI(title=settings.APP_NAME)

@app.get("/")
def root():
    return {"app": settings.APP_NAME}
```

**步骤 4**：验证导入
```bash
cd my_project
python -c "from shared.utils.config import get_settings; print(get_settings().APP_NAME)"
# 输出: MyProject
```

这就是 Monorepo 的基本工作方式——`shared/` 下的代码被 `services/` 直接引用，不需要任何安装步骤。

## 常见问题与排错

### Q1: `ModuleNotFoundError: No module named 'shared'`
**原因**：Python 找不到 `shared` 包。
**解决**：确保在项目根目录运行命令，或者执行 `pip install -e .` 以开发模式安装项目。

### Q2: 相对导入报错 `ImportError: attempted relative import with no known parent package`
**原因**：直接运行了使用相对导入的 `.py` 文件。
**解决**：改用绝对导入，或者通过 `python -m` 方式运行（如 `python -m services.api_service.main`）。

### Q3: `__init__.py` 里该写什么？
**原则**：只写"导出"代码——让外部引用更方便。不要在 `__init__.py` 里写业务逻辑。保持简短。

### Q4: 目录太深了怎么办？
GrassSea 最深路径是 `shared/models/postgres/project.py`，4 层。一般来说 Python 项目不超过 5 层是可以接受的。如果更深，考虑合并或重组。
