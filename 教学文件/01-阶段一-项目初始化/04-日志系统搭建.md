## 概念讲解

### 一、从 print 到结构化日志

每个 Python 初学者都用过 `print()` 调试：

```python
print("开始处理数据")
print(f"用户ID: {user_id}")
print(f"处理结果: {result}")
```

这在简单脚本中够用，但在生产环境中问题很大：

| 场景 | print 的问题 | 结构化日志的解决方案 |
|------|-------------|---------------------|
| 日志太多 | 无法按级别过滤 | `logger.debug()` / `logger.info()` / `logger.error()` |
| 查找特定用户 | 需要 grep + 人工解析 | `logger.info("user_action", user_id="123")` ← 结构化字段 |
| 服务器分析 | 纯文本难以被 ELK/Loki 索引 | JSON 格式，自动字段提取 |
| 跟踪一个请求 | 多个服务间找不到关联 | Trace ID 注入，一条链贯穿所有日志 |
| 生产环境 | print 输出到 stdout 没有时间戳 | structlog 自动加时间戳、日志级别、模块名 |

**结构化日志 vs 传统日志对比：**

```
传统日志（纯文本）:                      结构化日志（JSON）:

2024-01-15 10:30:01 User 123 login    {"timestamp":"2024-01-15T10:30:01",
                                        "level":"info",
                                        "event":"user_login",
                                        "user_id":"123",
                                        "ip":"192.168.1.1"}
```

在日志分析平台（如 ELK、Grafana Loki），结构化日志可以直接按 `user_id` 字段过滤和聚合，不需要写复杂的正则表达式。

### 二、日志级别

日志有五个标准级别，从低到高：

```
DEBUG    → INFO    → WARNING            → ERROR      → CRITICAL
调试信息   常规信息   警告（可能有问题）      错误（已出问题）  严重错误（服务挂了）

第1级      第2级      第3级                第4级          第5级
(10)       (20)       (30)                (40)           (50)
```

**使用场景：**

| 级别 | 什么时候用 | 示例 |
|------|-----------|------|
| DEBUG | 开发时了解程序内部状态 | "SQL 查询: SELECT * FROM users WHERE id=42" |
| INFO | 记录正常业务流程 | "用户登录成功"、"模型调用完成" |
| WARNING | 不正常但可恢复 | "主模型不可用，切换到备选模型" |
| ERROR | 出了问题需要关注 | "数据库连接失败，重试 3 次后放弃" |
| CRITICAL | 服务即将崩溃 | "磁盘空间不足，无法写入数据" |

**设置日志级别的作用**：生产环境通常设置为 INFO（屏蔽 DEBUG），开发环境设置为 DEBUG（显示所有日志）。在 GrassSea 中：

```python
setup_logging(level="DEBUG" if settings.APP_DEBUG else "INFO")
```

### 三、Trace ID —— 分布式追踪的核心

在微服务架构中，一个用户请求可能经过多个服务：

```
用户 → API Gateway → Agent Service → Model Gateway → LLM API
        (服务A)        (服务B)          (服务C)
```

如果没有 Trace ID，当 LLM 返回错误时，你只能看到 Model Gateway 的日志。要回溯到原始用户请求几乎不可能。

**有了 Trace ID**，整个请求链路上的所有日志都带有同一个 ID：

```
[Trace:abc123] API Gateway: 收到请求
[Trace:abc123] Agent Service: 意图识别 = "knowledge_qa"
[Trace:abc123] Model Gateway: 路由到 deepseek-chat
[Trace:abc123] Model Gateway: LLM 返回错误 "rate limit exceeded"
[Trace:abc123] API Gateway: 返回 502 给用户
```

在日志平台搜索 `abc123`，就能看到完整的请求轨迹。

## 项目代码精讲

现在逐段解析 GrassSea 的日志模块 `shared/utils/logging.py`。

### 第 1 段：ContextVar —— 线程安全的上下文变量

```python
from contextvars import ContextVar

# 分布式追踪上下文变量
_trace_id: ContextVar[str | None] = ContextVar("trace_id", default=None)
_span_id: ContextVar[str | None] = ContextVar("span_id", default=None)
```

`ContextVar` 是 Python 3.7+ 引入的机制，用于在异步环境中安全地存储"线程局部"数据。

**为什么需要 ContextVar？**

在异步编程中，多个请求可能在同一个线程中交替执行：

```
时间线: 请求A开始 → 请求B开始 → 请求A继续 → 请求B继续
```

如果用全局变量存储 trace_id，请求 B 会覆盖请求 A 的值。`ContextVar` 保证每个异步上下文有自己的变量副本，互不干扰。

```
类比：ContextVar 像是一个"便签本"

普通全局变量 = 一块白板，所有人共用（互相覆盖）
ContextVar   = 每个人的便签，贴在自己手上（互不影响）
```

### 第 2 段：add_trace_context —— 注入追踪信息

```python
def add_trace_context(
    logger: structlog.BoundLogger, method_name: str, event_dict: dict
) -> dict:
    """将追踪 ID 注入日志事件"""
    trace_id = _trace_id.get()
    span_id = _span_id.get()
    if trace_id:
        event_dict["trace_id"] = trace_id
    if span_id:
        event_dict["span_id"] = span_id
    return event_dict
```

这是一个 **structlog processor**（处理器）。每次记录日志时，structlog 会把日志事件通过一系列 processor 处理。这个 processor 负责把当前 ContextVar 中的 trace_id 和 span_id 注入到日志字典中。

**工作流程：**

```
1. 请求到达 → set_trace_id("abc123")  ← 设置 ContextVar
2. 业务代码 → logger.info("processing", data=...)
3. structlog 处理链:
   a. add_log_level         → 加 level 字段
   b. TimeStamper           → 加 timestamp 字段
   c. add_trace_context     → 加 trace_id="abc123"  ← 自动注入！
   d. JSONRenderer          → 输出 JSON
```

### 第 3 段：setup_logging —— 核心配置函数

```python
def setup_logging(level: str = "INFO", json_format: bool = True) -> None:
```

这个函数做了三件事：配置 structlog 处理器链、设置输出格式（JSON 或控制台友好格式）、设置日志级别。

#### 处理器链（processors）

```python
    shared_processors = [
        structlog.stdlib.add_log_level,           # 1. 添加日志级别
        structlog.stdlib.add_logger_name,         # 2. 添加 logger 名称
        structlog.processors.TimeStamper(fmt="iso"), # 3. 添加 ISO 时间戳
        add_trace_context,                        # 4. 注入 trace_id
        structlog.stdlib.PositionalArgumentsFormatter(), # 5. 格式化 %s 参数
        structlog.processors.StackInfoRenderer(), # 6. 添加堆栈信息
        structlog.processors.format_exc_info,     # 7. 格式化异常信息
        structlog.processors.UnicodeDecoder(),    # 8. 处理 Unicode
    ]
```

每个 processor 按顺序执行，层层添加信息。最终一条日志经过这 8 个 processor 后，从一个简单的 `event_dict` 变成了包含时间戳、级别、追踪 ID 的完整日志记录。

#### 渲染器选择

```python
    if json_format:
        renderer = structlog.processors.JSONRenderer()
    else:
        renderer = structlog.dev.ConsoleRenderer()
```

- `JSONRenderer`：输出 JSON 格式，适合生产环境（可被日志收集工具解析）
- `ConsoleRenderer`：带颜色的控制台输出，适合开发环境（人眼阅读友好）

#### structlog.configure —— 全局配置

```python
    structlog.configure(
        processors=shared_processors + [
            structlog.stdlib.ProcessorFormatter.wrap_for_formatter
        ],
        context_class=dict,
        logger_factory=structlog.stdlib.LoggerFactory(),
        wrapper_class=structlog.stdlib.BoundLogger,
        cache_logger_on_first_use=True,
    )
```

structlog 的核心配置。关键参数：
- `logger_factory`：告诉 structlog 使用标准库 logging 作为底层
- `wrapper_class`：使用 BoundLogger（支持绑定上下文的 logger）
- `cache_logger_on_first_use=True`：缓存 logger 实例，避免重复创建

#### 与标准库 logging 集成

```python
    formatter = structlog.stdlib.ProcessorFormatter(
        foreign_pre_chain=shared_processors,
        processors=[
            structlog.stdlib.ProcessorFormatter.remove_processors_meta,
            renderer,
        ],
    )

    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(formatter)

    root_logger = logging.getLogger()
    root_logger.handlers.clear()
    root_logger.addHandler(handler)
    root_logger.setLevel(getattr(logging, level.upper(), logging.INFO))
```

这一段是 structlog 与 Python 标准库 logging 的桥接。因为很多第三方库（如 uvicorn、sqlalchemy）使用标准库 logging，这段配置确保它们的日志也能以结构化格式输出。

**降低第三方库日志噪音**：

```python
    for lib in ("uvicorn", "httpx", "pymongo", "motor", "aiokafka", "pika"):
        logging.getLogger(lib).setLevel(logging.WARNING)
```

这些第三方库在 INFO 级别会产生大量日志，调高到 WARNING 可以减少噪音。

### 第 4 段：get_logger —— 获取日志实例

```python
def get_logger(name: str | None = None) -> structlog.stdlib.BoundLogger:
    """获取结构化日志实例"""
    return structlog.get_logger(name or __name__)
```

使用方式：

```python

```

### 第 5 段：trace_span —— 追踪上下文管理器

```python
@contextmanager
def trace_span(trace_id: str, span_id: str | None = None):
    """设置分布式追踪上下文"""
    t = _trace_id.set(trace_id)
    s = _span_id.set(span_id) if span_id else None
    try:
        yield
    finally:
        _trace_id.reset(t)
        if s is not None:
            _span_id.reset(s)
```

这是 Python 上下文管理器（context manager）的典型用法。使用方式：

```python
with trace_span("abc123", "span-001"):
    logger.info("step_1")  # 自动带有 trace_id=abc123, span_id=span-001
    logger.info("step_2")  # 同上
# 退出 with 块后，trace_id 和 span_id 自动恢复
```

`_trace_id.set(value)` 会返回一个 token，后续 `_trace_id.reset(token)` 用于恢复旧值。这保证了离开 `with` 块后，上下文变量恢复到之前的状态。

## 手把手实践

### 任务：为一个 FastAPI 应用添加结构化日志

**步骤 1**：安装依赖

```bash
pip install structlog fastapi uvicorn
```

**步骤 2**：创建 `my_logging.py`（简化版日志配置）

```python
import logging
import sys
import structlog
from contextvars import ContextVar

_trace_id: ContextVar[str | None] = ContextVar("trace_id", default=None)

def add_trace_id(logger, method_name, event_dict):
    trace_id = _trace_id.get()
    if trace_id:
        event_dict["trace_id"] = trace_id
    return event_dict

def setup_logging():
    structlog.configure(
        processors=[
            structlog.stdlib.add_log_level,
            structlog.processors.TimeStamper(fmt="iso"),
            add_trace_id,
            structlog.processors.JSONRenderer(),
        ],
        logger_factory=structlog.stdlib.LoggerFactory(),
    )

    handler = logging.StreamHandler(sys.stdout)
    root_logger = logging.getLogger()
    root_logger.addHandler(handler)
    root_logger.setLevel(logging.INFO)

def get_logger(name=None):
    return structlog.get_logger(name or __name__)

def set_trace_id(tid: str):
    _trace_id.set(tid)
```

**步骤 3**：创建 `app.py`

```python
from fastapi import FastAPI, Request
from my_logging import setup_logging, get_logger, set_trace_id
import uuid

setup_logging()
logger = get_logger(__name__)
app = FastAPI()

@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    trace_id = str(uuid.uuid4())[:8]
    set_trace_id(trace_id)
    logger.info("request_start", method=request.method, path=request.url.path)
    response = await call_next(request)
    logger.info("request_end", status_code=response.status_code)
    return response

@app.get("/")
def root():
    logger.info("handling_root")
    return {"message": "Hello"}
```

**步骤 4**：运行并观察输出

```bash
uvicorn app:app --port 8000
# 访问 http://localhost:8000/
```

你会看到类似这样的 JSON 日志：

```json
{"event": "request_start", "method": "GET", "path": "/", "trace_id": "a1b2c3d4", "level": "info", "timestamp": "2024-01-15T10:30:01.123Z"}
{"event": "handling_root", "trace_id": "a1b2c3d4", "level": "info", "timestamp": "2024-01-15T10:30:01.124Z"}
{"event": "request_end", "status_code": 200, "trace_id": "a1b2c3d4", "level": "info", "timestamp": "2024-01-15T10:30:01.125Z"}
```

注意：同一个请求的所有日志都有相同的 `trace_id`！

## 常见问题与排错

### Q1: structlog 和标准库 logging 有什么区别？
structlog 是 logging 的"增强层"。它不替代 logging，而是在其之上提供结构化 API。你仍然可以使用 `logging.getLogger()`，但 structlog 会让你的日志更规范、更易分析。GrassSea 将两者集成在一起，确保所有日志（包括第三方库的）都通过统一管道输出。

### Q2: 日志太多怎么办？
有两个方法：
1. **提高日志级别**：将 INFO 改为 WARNING，只显示警告和错误
2. **降低第三方库日志**：在 `setup_logging` 中增加需要静音的库名

### Q3: ContextVar 在异步中真的安全吗？
是的。Python 的 asyncio 框架原生支持 ContextVar。每个 Task 有自己的上下文，ContextVar 的值不会在 Task 之间泄露。GrassSea 使用 `ContextVar` 而不是 `threading.local` 正是因为它是异步安全的。

### Q4: JSON 日志人类读起来不友好怎么办？
开发环境设置 `json_format=False`，使用 ConsoleRenderer 输出带颜色的友好格式。生产环境用 JSON。GrassSea 的 `setup_logging` 函数支持这个开关。
