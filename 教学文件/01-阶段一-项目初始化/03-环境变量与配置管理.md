## 概念讲解

### 一、为什么需要环境变量

假设你在写一个连接数据库的程序，最初可能是这样：

```python
# 错误示范：硬编码敏感信息
DB_HOST = "192.168.1.100"
DB_USER = "admin"
DB_PASSWORD = "MySecretPass123"
DB_NAME = "production"
```

这会带来三个严重问题：

**问题 1：安全风险。** 密码写在代码里，任何人拿到代码就能看到数据库密码。一旦上传到 GitHub，密码就永远留在 Git 历史中。

**问题 2：环境隔离困难。** 开发环境（本机）和生产环境（服务器）的数据库地址不同，但代码是一样的。如果硬编码，切换环境就得改代码。

**问题 3：团队协作困难。** 每个开发者的本机配置不同（端口、密码），硬编码会导致"在我机器上能跑"的问题。

**环境变量解决方案：**

```python
# 正确做法：从环境变量读取
import os

DB_HOST = os.getenv("DB_HOST", "localhost")
DB_USER = os.getenv("DB_USER", "admin")
DB_PASSWORD = os.getenv("DB_PASSWORD")  # 没有默认值，必须设置
```

运行方式：
```bash
# Linux/macOS
export DB_PASSWORD=MySecretPass123
python app.py

# Windows PowerShell
$env:DB_PASSWORD="MySecretPass123"
python app.py

# 或使用 .env 文件（推荐）
echo "DB_PASSWORD=MySecretPass123" > .env
python app.py
```

### 二、.env 文件的约定

`.env` 文件是存放环境变量的标准文件。GrassSea 提供了 `.env.example` 作为模板：

```
.env.example  = 模板文件（提交到 Git，不含真实密码）
.env          = 实际配置（不提交到 Git，在 .gitignore 中）
```

```
┌─────────────────────┐     ┌─────────────────────┐
│    .env.example     │     │       .env          │
│                     │     │                     │
│ DB_HOST=localhost   │     │ DB_HOST=localhost   │
│ DB_PASSWORD=change  │────>│ DB_PASSWORD=Myp@ss! │
│ API_KEY=your-key    │     │ API_KEY=sk-abc123   │
│                     │     │                     │
│ (提交到 Git)        │     │ (在 .gitignore 中)   │
└─────────────────────┘     └─────────────────────┘
```

GrassSea 的 `.env.example` 包含所有配置项及其默认值，方便新人快速上手。`.gitignore` 中明确忽略 `.env`：

```gitignore
# 环境变量
.env
.env.local
.env.*.local
```

### 三、pydantic-settings 的 BaseSettings

pydantic-settings 是 pydantic 生态中专门处理配置的库。它的核心是 `BaseSettings` 类，能自动从环境变量（包括 `.env` 文件）读取配置，并做类型验证。

```
传统 os.getenv 方式:                    pydantic-settings 方式:

os.getenv("PORT", "8000")              class Settings(BaseSettings):
手动类型转换                               PORT: int = 8000
难维护                                   自动类型转换 + 验证
                                                IDE 自动补全
```

## 项目代码精讲

### GrassSea 的 Settings 类详解

让我们逐段阅读 `shared/utils/config.py`：

#### 第 1 段：类声明和 model_config

```python
class Settings(BaseSettings):
    """应用全局配置"""

    model_config = SettingsConfigDict(
        env_file=".env",            # 从 .env 文件读取
        env_file_encoding="utf-8",  # 文件编码
        extra="ignore",             # 忽略未定义的环境变量
        case_sensitive=False,       # 环境变量名不区分大小写
    )
```

`SettingsConfigDict` 是配置字典，各字段含义：

| 配置项 | 含义 |
|--------|------|
| `env_file=".env"` | 指定环境变量文件名 |
| `extra="ignore"` | 如果 `.env` 中有未定义的变量，不报错 |
| `case_sensitive=False` | `APP_NAME` 和 `app_name` 都能匹配 |

**实际效果**：当你写了 `APP_NAME: str = "GrassSea"`，pydantic-settings 会按以下优先级查找值：

```
1. 系统环境变量 APP_NAME     (最高优先级)
2. .env 文件中的 APP_NAME
3. 代码中的默认值 "GrassSea" (最低优先级)
```

#### 第 2 段：应用和服务端口配置

```python
    # --- 应用 ---
    APP_NAME: str = "GrassSea"
    APP_VERSION: str = "0.1.0"
    APP_ENV: str = "development"
    APP_DEBUG: bool = True
    APP_SECRET_KEY: str = "change-me-in-production"

    # --- 服务端口 ---
    API_GATEWAY_PORT: int = 8000
    CHAT_SERVICE_PORT: int = 8001
    AGENT_SERVICE_PORT: int = 8002
    KNOWLEDGE_SERVICE_PORT: int = 8003
    MODEL_GATEWAY_PORT: int = 8004
```

这里注意 `APP_DEBUG: bool = True` —— pydantic-settings 会自动将字符串 `"true"` / `"false"` 转换为 Python 的布尔值。

端口号的编排规律：8000 是 API 网关，后续服务依次递增。这种约定让开发者无需查文档就能知道每个服务的端口。

#### 第 3 段：PostgreSQL 配置与 `@property` 计算属性

```python
    # --- PostgreSQL 15 + TimescaleDB ---
    POSTGRES_HOST: str = "localhost"
    POSTGRES_PORT: int = 5432
    POSTGRES_USER: str = "grasssea"
    POSTGRES_PASSWORD: str = "grasssea"
    POSTGRES_DB: str = "grasssea"

    @property
    def POSTGRES_URI(self) -> str:
        return (
            f"postgresql+asyncpg://{self.POSTGRES_USER}:{self.POSTGRES_PASSWORD}"
            f"@{self.POSTGRES_HOST}:{self.POSTGRES_PORT}/{self.POSTGRES_DB}"
        )

    @property
    def POSTGRES_SYNC_URI(self) -> str:
        return (
            f"postgresql://{self.POSTGRES_USER}:{self.POSTGRES_PASSWORD}"
            f"@{self.POSTGRES_HOST}:{self.POSTGRES_PORT}/{self.POSTGRES_DB}"
        )
```

**这里的巧妙设计**：数据库连接 URI 不是直接配置的，而是通过 `@property` **计算出来的**。

为什么不直接写 `POSTGRES_URI = "postgresql+asyncpg://..."`？

1. **避免冗余** — 如果同时配置了独立字段和完整 URI，改了 HOST 还要改 URI，容易出错
2. **拼接逻辑统一** — 所有 URI 的拼接逻辑在一处，格式统一
3. **灵活性** — 某些场景需要异步 URI (`+asyncpg`)，某些场景需要同步 URI，通过两个 property 轻松区分

**数据库 URI 格式说明**：

```
postgresql+asyncpg://用户名:密码@主机:端口/数据库名
│         │         │      │     │   │     │
│         └─ 驱动    │      │     │   │     └─ 数据库名
│                    │      │     │   └─────── 端口
└─ 协议              用户名  密码  主机
```

#### 第 4 段：MongoDB 和 Redis 配置

```python
    # --- MongoDB 7 ---
    MONGODB_HOST: str = "localhost"
    MONGODB_PORT: int = 27017
    MONGODB_USER: str = "grasssea"
    MONGODB_PASSWORD: str = "grasssea"
    MONGODB_DB: str = "grasssea"

    @property
    def MONGODB_URI(self) -> str:
        return (
            f"mongodb://{self.MONGODB_USER}:{self.MONGODB_PASSWORD}"
            f"@{self.MONGODB_HOST}:{self.MONGODB_PORT}/{self.MONGODB_DB}"
        )

    # --- Redis 7 ---
    REDIS_HOST: str = "localhost"
    REDIS_PORT: int = 6379
    REDIS_PASSWORD: str = ""     # 注意：密码可为空
    REDIS_DB: int = 0

    @property
    def REDIS_URI(self) -> str:
        if self.REDIS_PASSWORD:
            return f"redis://:{self.REDIS_PASSWORD}@{self.REDIS_HOST}:{self.REDIS_PORT}/{self.REDIS_DB}"
        return f"redis://{self.REDIS_HOST}:{self.REDIS_PORT}/{self.REDIS_DB}"
```

Redis 的 URI 拼接中有一个细节：当密码为空时，URI 格式不同（不需要 `:` 前缀）。这就是 `@property` 的价值——封装了格式逻辑，使用者不需要关心细节。

#### 第 5 段：LLM API Keys（安全关键）

```python
    # --- LLM API Keys (通过环境变量注入) ---
    DEEPSEEK_API_KEY: str = ""
    DEEPSEEK_BASE_URL: str = "https://api.deepseek.com"
    CLAUDE_API_KEY: str = ""
    CLAUDE_BASE_URL: str = "https://api.anthropic.com"
    OPENAI_API_KEY: str = ""
    OPENAI_BASE_URL: str = "https://api.openai.com/v1"
```

这些 API Key 的默认值是空字符串，意味着**必须通过环境变量注入**。这是一种安全设计——代码中不包含任何真实的 API Key。

`.env.example` 中对应的行：

```bash
DEEPSEEK_API_KEY=your-deepseek-api-key
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

新手复制 `.env.example` 为 `.env`，填入真实的 Key，就完成了配置。

#### 第 6 段：`@lru_cache` 单例模式

```python
@lru_cache
def get_settings() -> Settings:
    """获取全局配置单例"""
    return Settings()
```

这是整个模块最关键的一行。`@lru_cache` 是 Python 标准库 `functools` 中的缓存装饰器。在这里，它的作用是实现**单例模式**。

**单例模式的工作原理**：

```python
# 第一次调用：创建 Settings 实例，缓存起来
settings1 = get_settings()   # 创建 Settings()，读取 .env 文件

# 后续调用：直接返回缓存的实例
settings2 = get_settings()   # 不重新创建，返回同一个对象

# settings1 和 settings2 是同一个对象
assert settings1 is settings2  # True
```

**为什么需要单例？**

1. **性能** — `.env` 文件只读取一次，不是每次调用都读
2. **一致性** — 整个应用使用同一个配置对象，不会出现"一个改了一个没改"的问题
3. **简洁** — 任何模块只需要 `get_settings()` 就能拿到配置，不需要传参

### 完整使用流程

```
1. 开发者复制 .env.example -> .env，填入真实值
2. 应用启动时，任意模块调用 get_settings()
3. pydantic-settings 读取 .env 文件 + 系统环境变量
4. 类型验证：PORT 必须是 int，DEBUG 自动转换为 bool
5. 如果缺少必要配置或有类型错误，启动时立即报错（fail-fast）
6. 运行时任何模块调用 get_settings() 都返回同一个实例
```

## 手把手实践

### 任务：创建一个带数据库的配置模块

**步骤 1**：安装 pydantic-settings

```bash
pip install pydantic-settings python-dotenv
```

**步骤 2**：创建 `.env` 文件

```bash
# .env
APP_NAME=MyApp
APP_DEBUG=true
DB_HOST=localhost
DB_PORT=5432
DB_USER=myuser
DB_PASSWORD=mypass
DB_NAME=mydb
```

**步骤 3**：创建 `config.py`

```python
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
    )

    APP_NAME: str = "DefaultApp"
    APP_DEBUG: bool = False
    DB_HOST: str = "localhost"
    DB_PORT: int = 5432
    DB_USER: str = "postgres"
    DB_PASSWORD: str = ""
    DB_NAME: str = "postgres"

    @property
    def DB_URI(self) -> str:
        return (
            f"postgresql://{self.DB_USER}:{self.DB_PASSWORD}"
            f"@{self.DB_HOST}:{self.DB_PORT}/{self.DB_NAME}"
        )

@lru_cache
def get_settings() -> Settings:
    return Settings()

# 测试
if __name__ == "__main__":
    s = get_settings()
    print(f"App: {s.APP_NAME}, Debug: {s.APP_DEBUG}")
    print(f"DB URI: {s.DB_URI}")
```

**步骤 4**：运行验证

```bash
python config.py
# 输出:
# App: MyApp, Debug: True
# DB URI: postgresql://myuser:mypass@localhost:5432/mydb
```

**步骤 5**：验证类型转换

```python
# 添加到 config.py 末尾
s2 = get_settings()
print(type(s2.APP_DEBUG))   # <class 'bool'>  ← 自动从字符串 "true" 转换
print(type(s2.DB_PORT))     # <class 'int'>   ← 自动从字符串 "5432" 转换
print(s is s2)              # True           ← 单例模式生效
```

## 常见问题与排错

### Q1: `.env` 文件改了但配置没变化
**原因**：`@lru_cache` 缓存了第一次创建的 Settings 实例。
**解决**：重启应用。这是设计如此——运行时不重新读 `.env`。

### Q2: `ValidationError: 1 validation error`
**原因**：某个字段的类型转换失败（如把 `"abc"` 赋给了 `int` 字段）。
**解决**：检查 `.env` 文件中对应字段的值是否符合类型定义。`bool` 字段只接受 `true/false/1/0/yes/no`（不区分大小写）。

### Q3: API Key 不小心提交到 Git 了怎么办？
**解决步骤**：
```bash
# 1. 立即更换 Key（在对应平台重新生成）
# 2. 从 Git 历史中清除
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env" \
  --prune-empty --tag-name-filter cat -- --all
# 3. 确认 .gitignore 中包含 .env
echo ".env" >> .gitignore
```

### Q4: 如何在 Docker 中使用 `.env`？
Docker Compose 会自动读取同目录的 `.env` 文件作为变量。GrassSea 的 `docker-compose.yml` 中使用了 `${POSTGRES_USER:-grasssea}` 语法，冒号后面是默认值。
