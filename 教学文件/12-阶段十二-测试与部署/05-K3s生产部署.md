## 概念讲解

### Kubernetes 核心抽象（一句话理解）

Kubernetes 是容器编排平台。想象你有一个"数据中心"，K8s 帮你在里面管理容器的运行。

```
Kubernetes 核心抽象 —— 用"搬家公司"做类比:

  Pod (容器组)
  ┌──────────────────────────────────────────┐
  │ 一个 Pod = 一个"搬运箱"                  │
  │ 里面装一个或多个容器（通常是1个）         │
  │ 是 K8s 调度的最小单位                    │
  │ 例: agent-service 的一个实例             │
  └──────────────────────────────────────────┘

  Deployment (部署)
  ┌──────────────────────────────────────────┐
  │ 管理 Pod 的"工头"                        │
  │ 告诉 K8s: "我永远要 3 个 agent-service   │
  │           的 Pod 在运行"                 │
  │ 少一个就自动补上，挂一个就自动替换        │
  └──────────────────────────────────────────┘

  Service (服务)
  ┌──────────────────────────────────────────┐
  │ Pod 的"前台接待"                         │
  │ Pod 的 IP 会变（重启后），Service 提供   │
  │ 一个固定的 IP 和 DNS 名                  │
  │ 例: agent-service.grasssea.svc.cluster.local │
  └──────────────────────────────────────────┘

  Ingress (入口)
  ┌──────────────────────────────────────────┐
  │ 集群的"大门"                             │
  │ 把外部 HTTP 请求路由到对应的 Service     │
  │ /api → agent-service                     │
  │ /v1  → model-gateway                     │
  │ /    → frontend                          │
  └──────────────────────────────────────────┘
```

### K3s vs K8s

K3s 是 Rancher 开发的轻量级 Kubernetes 发行版：

```
标准 K8s (kubeadm):
┌──────────────────────────────────────────┐
│ 完整功能集，适合大规模集群（50+ 节点）    │
│ 安装包 ~1GB，内存占用 ~1GB              │
│ 适合: 企业数据中心、大型云集群           │
└──────────────────────────────────────────┘

K3s:
┌──────────────────────────────────────────┐
│ 裁剪了云厂商特性和 alpha 功能             │
│ 安装包 ~50MB，内存占用 ~500MB           │
│ 使用 SQLite 替代 etcd（更轻量）          │
│ 内置了 Traefik Ingress 和 local-path 存储 │
│ 适合: 边缘计算、物联网、小型团队         │
└──────────────────────────────────────────┘

GrassSea 选择 K3s 的原因:
  - 团队规模小，不需要大规模集群
  - 资源有限（一台服务器跑所有服务）
  - K3s 足够满足需求，运维简单
```

### Pod 的生命周期

```
Pod 从创建到运行:

  Pending ──▶ Running ──▶ Succeeded (正常退出)
                │
                ├──▶ Failed (异常退出)
                │
                └──▶ CrashLoopBackOff (反复崩溃)

  Deployment 担保 Pod 永远在 Running 状态:
  Running Pod 挂了 → Deployment 检测到 → 创建新 Pod → 新 Pod 替代旧 Pod
```

## 项目代码精讲

GrassSea 的 K3s 配置在 `infrastructure/k3s/` 目录下。

### Namespace — 资源隔离

```yaml
# infrastructure/k3s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: grasssea
  labels:
    app.kubernetes.io/name: grasssea
    app.kubernetes.io/part-of: grasssea-platform
```

Namespace 就像一个"项目文件夹"，把 GrassSea 的所有资源组织在一起。好处：
- 不同项目互不干扰（另一个项目在 `other-app` namespace）
- 一次删除整个 namespace 就清理了所有资源
- 可以为不同 namespace 设置不同的资源配额

### ConfigMap — 非敏感配置

```yaml
# infrastructure/k3s/configmap.yaml（关键部分）
apiVersion: v1
kind: ConfigMap
metadata:
  name: grasssea-config
  namespace: grasssea
data:
  APP_NAME: "GrassSea"
  APP_ENV: "production"
  POSTGRES_HOST: "postgres.grasssea.svc.cluster.local"
  POSTGRES_PORT: "5432"
  REDIS_HOST: "redis.grasssea.svc.cluster.local"
  MILVUS_HOST: "milvus.grasssea.svc.cluster.local"
```

**逐段解析**：

1. `kind: ConfigMap` — 声明这是一个 ConfigMap（配置字典）资源。

2. `data:` — 键值对形式的配置数据。Pod 可以通过环境变量或文件挂载的方式读取这些配置。

3. `POSTGRES_HOST: "postgres.grasssea.svc.cluster.local"` — 这是 **Kubernetes 内部 DNS**。格式为 `<服务名>.<命名空间>.svc.cluster.local`。每个 Service 都会自动获得这个 DNS 名，Pod 通过这个名字访问其他服务，而不是硬编码 IP。

4. 注意：ConfigMap 只存非敏感配置（主机名、端口、开关等）。密码和 API Key 应放在 Secret 中。

### Secret — 敏感信息

```yaml
# infrastructure/k3s/secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: grasssea-secrets
  namespace: grasssea
type: Opaque
stringData:
  APP_SECRET_KEY: "change-me-in-production"
  POSTGRES_PASSWORD: "grasssea"
  DEEPSEEK_API_KEY: ""
  CLAUDE_API_KEY: ""
```

**逐段解析**：

1. `type: Opaque` — 通用密钥类型（区别于 `kubernetes.io/tls` 等特定类型）。

2. `stringData:` — 明文数据。K8s 会自动将其 Base64 编码存储。注意：Base64 只是编码，不是加密！任何人都可以解码。K3s 的 Secret 真正的安全性来自于：
   - RBAC 权限控制（只有授权的 Pod 能读取）
   - 静态加密（K3s 支持加密存储 Secret）
   - 审计日志（记录谁访问了 Secret）

3. API Key 为空字符串 — 生产环境中这些值通过 Sealed Secrets 或 HashiCorp Vault 注入，不会明文写在 YAML 中。代码中的注释 `# 实际值通过 sealed-secrets 或 vault 管理` 说明了这一点。

### Ingress — 外部流量入口

```yaml
# infrastructure/k3s/ingress.yaml
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["grasssea.local"]
      secretName: grasssea-tls
  rules:
    - host: grasssea.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: agent-service
                port: { number: 8002 }
          - path: /v1
            pathType: Prefix
            backend:
              service:
                name: model-gateway
                port: { number: 8004 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port: { number: 80 }
```

**逐段解析**：

1. `ingressClassName: nginx` — 使用 Nginx Ingress Controller 处理入站流量。

2. `tls:` — TLS/SSL 配置。HTTPS 证书存储在 Secret `grasssea-tls` 中。

3. `rules:` — 路由规则（按路径分发）：
   - `/api` → agent-service（智能体服务）
   - `/v1` → model-gateway（模型网关）
   - `/` → frontend（前端）

4. `pathType: Prefix` — 前缀匹配。`/api/xxx/yyy` 也会匹配到 `/api` 规则。

**路由顺序很重要**：`/` 放在最后（它是兜底规则），`/api` 和 `/v1` 放在前面。如果 `/` 排在前面，所有请求都会被前端服务拦截，API 请求无法到达后端。

### PersistentVolumeClaim — 持久存储

```yaml
# infrastructure/k3s/persistent-volumes.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: grasssea
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests: { storage: 50Gi }
  storageClassName: local-path
```

**逐段解析**：

1. `PersistentVolumeClaim` (PVC) — "存储申请单"。Pod 说"我需要 50GB 的存储空间"，K3s 帮忙分配。

2. `accessModes: ["ReadWriteOnce"]` — 只能被一个 Pod 以读写方式挂载。对于数据库来说这是必需的（多个 Pod 同时写会损坏数据）。

3. `storage: 50Gi` — 请求 50GB 存储。`Gi` = Gibibyte (1024^3 bytes)。

4. `storageClassName: local-path` — K3s 内置的本地存储类。数据直接存在节点磁盘上（而不是网络存储）。

GrassSea 为四个有状态服务各申请了 PVC：PostgreSQL (50Gi)、MongoDB (30Gi)、MinIO (100Gi)、Milvus (50Gi)。无状态服务（如 chat-service）不需要 PVC——它们的数据存在数据库中，本身不存数据。

## 常见问题与排错

**Q1：Pod 一直在 CrashLoopBackOff 怎么办？**

A：使用 `kubectl describe pod <pod-name> -n grasssea` 查看事件，`kubectl logs <pod-name> -n grasssea` 查看日志。常见原因：1) 数据库密码错误（Secret 未正确加载）；2) 依赖的数据库服务未就绪；3) 资源不足（内存/CPU）。

**Q2：Service 的 DNS 名解析不了？**

A：确认 Service 和 Pod 在同一个 Namespace 中。跨 Namespace 需要完整 DNS 名：`<service>.<namespace>.svc.cluster.local`。

**Q3：`kubectl apply` 和 `kubectl create` 有什么区别？**

A：`apply` 是声明式的（推荐）：告诉 K8s "我要达到这个状态"，K8s 自动计算需要做什么。`create` 是命令式的：直接创建资源，如果资源已存在会报错。总是优先使用 `apply`。

**Q4：PVC 绑定不了 PV？**

A：检查 `storageClassName` 是否匹配。K3s 默认使用 `local-path`。如果使用其他 StorageClass（如 `longhorn`、`rook-ceph`），需要先安装对应的 CSI 驱动。
