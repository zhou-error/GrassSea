## 概念讲解

### 一、数据库不是"一刀切"的

新手常犯的一个错误是："所有数据都存 MySQL / PostgreSQL 就行了吧？"

在简单应用中（如个人博客）确实可以。但在 GrassSea 这样的复杂系统中，不同数据有不同的特征，需要不同的数据库来高效处理。

```
数据特征分类：

1. 结构化数据（关系型）     → PostgreSQL
   - 有固定的列和类型
   - 数据之间有外键关联
   - 需要事务保证一致性
   例如：用户、项目、任务

2. 半结构化/无结构数据      → MongoDB
   - 字段不固定，每条记录可以不同
   - JSON 格式，嵌套结构
   - 写多读少，不需要复杂关联
   例如：对话记录、审查报告

3. 向量数据（语义相似度）   → Milvus
   - 高维浮点数数组（如 3072 维）
   - 需要计算"最相似的 K 个"
   - 传统数据库无法高效处理
   例如：知识库文档的语义索引

4. 时序数据                → TimescaleDB (PG 扩展)
   - 按时间自动分区
   - 聚合查询为主
   - 数据量大且持续增长
   例如：Token 统计、API 延迟

5. 高速缓存                → Redis
   - 微秒级响应
   - 数据可以过期自动删除
   - 常用于计数器、分布式锁
   例如：会话缓存、限流计数

6. 图数据（实体关系）       → Neo4j
   - 节点和边组成的网络
   - 关系查询比 SQL JOIN 快 1000 倍
   例如：船舶零部件父子关系、规范条文引用关系
```

### 三、为什么 GrassSea 使用这么多数据库

#### 决策 1：为什么不让 PostgreSQL 包办所有数据？

PostgreSQL 确实很强大——它有 JSONB 列（可以存文档）、有 pgvector 扩展（可以存向量）、有 TimescaleDB（可以存时序）。理论上可以把所有数据塞进去。

但 GrassSea 选择多数据库的原因：

**1. 专业性** — Milvus 的向量检索性能比 pgvector 高一个数量级。对于 RAG 系统来说，检索速度直接影响用户体验。

**2. 弹性扩展** — MongoDB 的水平扩展比 PostgreSQL 简单得多。对话记录每天增长很快，MongoDB 的 sharding 可以轻松应对。

**3. 职责分离** — 不同类型的数据用不同的数据库，故障不会互相影响。MongoDB 挂了不影响用户登录（PostgreSQL），Redis 挂了只影响缓存不影响核心数据。

**4. 最佳实践** — 业界共识：每种数据库做好一件事。

#### 决策矩阵

| 数据 | 特征 | 最适合的数据库 | 备选 |
|------|------|---------------|------|
| 用户信息 | 固定结构、外键关联、需要事务 | PostgreSQL | — |
| 项目记录 | 固定结构、与用户/任务关联 | PostgreSQL | — |
| 型值表 | 船舶领域专用、结构化 | PostgreSQL (JSONB备选) | — |
| 对话记录 | 嵌套结构、字段不固定、量大 | MongoDB | PostgreSQL JSONB |
| 审查报告 | 半结构化、含数组、无需JOIN | MongoDB | PostgreSQL JSONB |
| 知识库文档向量 | 3072 维向量、ANN 检索 | Milvus | pgvector |
| Token 统计 | 时间维、聚合查询、数据量大 | TimescaleDB | PostgreSQL |
| 会话状态 | 临时数据、微秒响应、自动过期 | Redis | — |
| 限流计数 | 高频读写、自动过期 | Redis | — |

### 四、选型决策框架

当你需要为一个新数据选型时，可以按这个顺序问自己：

```
1. 数据有固定结构吗？
   └─ 是 → 关系型数据库 (PostgreSQL)
   └─ 否 → 文档数据库 (MongoDB)

2. 需要计算"语义相似度"吗？
   └─ 是 → 向量数据库 (Milvus)

3. 数据按时间快速增长吗？
   └─ 是 → 时序数据库 (TimescaleDB)

4. 数据是临时的、需要极快读写吗？
   └─ 是 → 缓存数据库 (Redis)

5. 数据是高度关联的网络结构吗？
   └─ 是 → 图数据库 (Neo4j)
```

## 项目代码精讲

GrassSea 中的数据库选型体现在两个关键文件中：

### `shared/models/database.py` — 连接管理

这个文件为每种数据库创建了独立的连接：

```python
# PostgreSQL — SQLAlchemy async engine + session factory
pg_engine = create_async_engine(settings.POSTGRES_URI, pool_size=20)
pg_session_factory = async_sessionmaker(pg_engine, class_=AsyncSession)

# MongoDB — Motor (async)
mongo_client: AsyncIOMotorClient | None = None
async def init_mongodb():
    global mongo_client
    mongo_client = AsyncIOMotorClient(settings.MONGODB_URI)

# Redis — redis-py (async)
redis_client: Redis | None = None
async def init_redis():
    global redis_client
    redis_client = Redis.from_url(settings.REDIS_URI)

# Milvus — pymilvus (sync)
from pymilvus import connections
def init_milvus():
    connections.connect(host=settings.MILVUS_HOST, port=settings.MILVUS_PORT)
```

### `docker-compose.yml` — 数据中心

Docker Compose 中每个数据库都是一个独立服务：

```
postgres   → PostgreSQL 15 + TimescaleDB
mongodb    → MongoDB 7
redis      → Redis 7
milvus     → Milvus 2.4 (+ etcd + MinIO 子服务)
neo4j      → Neo4j 5 (可选，通过 profiles 控制)
```

### 任务：为一个简单场景做数据库选型

假设你要开发一个图书管理系统，有以下数据：

1. **图书信息**（书名、作者、ISBN、分类、库存、位置）
2. **借阅记录**（借书人、借书时间、还书时间、状态）
3. **书评**（评分、评论内容、点赞数、标签）
4. **热门图书缓存**（每日更新，展示在首页）
5. **图书推荐**（根据用户阅读历史推荐相似书籍）

**请思考并回答**：
- 哪些数据适合 PostgreSQL？为什么？
- 哪些数据适合 MongoDB？为什么？
- 哪些适合 Redis？为什么？
- 推荐功能需要什么数据库？为什么？

**参考答案**：

| 数据 | 数据库 | 理由 |
|------|--------|------|
| 图书信息 | PostgreSQL | 固定结构、需要事务（入库/出库） |
| 借阅记录 | PostgreSQL | 与图书表关联、需要事务 |
| 书评 | MongoDB | 字段灵活（不同书标签不同）、嵌套结构（评论+回复） |
| 热门图书 | Redis | 临时数据、每日过期、高频读取 |

## 常见问题与排错

### Q1: 数据库太多了会不会很难维护？
确实增加了运维复杂度。GrassSea 的策略是：
- 开发环境：Docker Compose 一键启动所有数据库
- 生产环境：核心数据库（PG, Mongo, Redis）高可用部署，Milvus 和 Neo4j 按需启用
- 学习曲线：团队只需要深入掌握 PG，其他库只需要基础操作

### Q2: 可以只用 PostgreSQL 的 JSONB 替代 MongoDB 吗？
技术上可以，但 MongoDB 在大规模文档存储、水平扩展、聚合管道方面有优势。GrassSea 选择 MongoDB 是基于"对话记录会快速增长"的预判。

### Q3: Redis 数据丢了怎么办？
Redis 不是主存储，数据丢失不影响业务（缓存重建即可）。GrassSea 启用了 Redis AOF 持久化（`--appendonly yes`），重启后数据不会丢失。但对缓存数据的丢失，系统设计本身就假设了"缓存可能为空"。
