## 概念讲解

### 服务间通信的三个层次

在微服务架构中，服务之间的通信可以分为三个层次：

```
层1: 同步请求-响应  ->  httpx (HTTP/REST)  ->  即时回答，需要等待结果
层2: 高性能二进制    ->  gRPC              ->  微秒级延迟，内部高频调用
层3: 异步消息       ->  RabbitMQ / Kafka  ->  解耦，削峰填谷，可靠投递
```

### 三种通信模式对比

```
HTTP/httpx:
  服务A  --[POST /api]--> 服务B
  服务A  <--[JSON]------ 服务B
  特点：同步等待，简单直观，适合请求-响应

gRPC:
  服务A  --[protobuf]--> 服务B
  服务A  <--[protobuf]-- 服务B
  特点：二进制序列化，强类型，快速，适合高频内部RPC

消息队列 (RabbitMQ):
  服务A  --[消息]--> [Broker] --[消息]--> 服务B
  特点：异步解耦，持久化投递，适合任务分发
```

### GrassSea 的选型

```
                        选型
    场景                方式          原因
    ──────────────────────────────────────────
    Chat -> Agent       httpx        请求-响应，需要立即返回
    Chat -> Knowledge   httpx        同上
    Agent -> LLM        httpx        OpenAI API 已是 HTTP
    Agent -> RAG        httpx        内部 HTTP API
    任务通知            WebSocket    实时推送进度
    未来：大规模任务    消息队列      任务可排队异步处理
```

GrassSea 目前以 httpx 为主。这是合理的初级阶段选型——当系统规模增大后，再引入 gRPC 或消息队列。

## 项目代码精讲

**文件位置**: `services/agent_service/main.py`

### 1. 同步调用 LLM（闲聊处理）

```python
async def _handle_chitchat(message: str) -> str:
    """处理闲聊 — 直接调用 LLM"""
    import httpx
    if not settings.DEEPSEEK_API_KEY:
        return "您好！我是 GrassSea AI 助手..."

    async with httpx.AsyncClient(timeout=30) as client:
        resp = await client.post(
            f"{settings.DEEPSEEK_BASE_URL}/v1/chat/completions",
            headers={"Authorization": f"Bearer {settings.DEEPSEEK_API_KEY}"},
            json={
                "model": "deepseek-chat",
                "messages": [{"role": "user", "content": message}],
                "max_tokens": 1024,
            },
        )
        data = resp.json()
        return data["choices"][0]["message"]["content"]
```

**逐段解析**：

这是一个典型的"装饰器模式"应用——在核心 LLM 调用外面，包了一层参数组装和响应解析。

1. `if not settings.DEEPSEEK_API_KEY` — **防御性编程**。如果用户忘记配置 API Key，返回友好的中文提示而不是崩溃。这是生产代码的习惯。

2. `async with httpx.AsyncClient(timeout=30) as client:` — 创建 HTTP 客户端，30 秒超时。LLM 生成可能需要几秒（思考 + token 生成），30 秒足够。

3. `Authorization: Bearer {settings.DEEPSEEK_API_KEY}` — 这是 OpenAI 兼容 API 的标准鉴权方式。DeepSeek / Claude / OpenAI 都用同样的格式。

4. `resp.json()` — 将响应体解析为 Python dict。如果 LLM 返回非 JSON（罕见但可能），这里会抛出异常。

5. `data["choices"][0]["message"]["content"]` — 从 OpenAI 格式的响应中提取文本内容。这个路径是 OpenAI API 的标准格式。

### 2. 同步调用 RAG 引擎（知识查询）

```python
async def _handle_knowledge_query(message: str, session_id: str) -> dict:
    """处理知识查询 — 调用 RAG 引擎"""
    import httpx
    try:
        async with httpx.AsyncClient(timeout=60) as client:
            resp = await client.post(
                f"http://localhost:{settings.KNOWLEDGE_SERVICE_PORT}/rag/query",
                json={"query": message, "top_k": 5},
            )
            if resp.status_code == 200:
                data = resp.json()
                return {"answer": data["answer"], "sources": data.get("sources", [])}
    except Exception as e:
        logger.error("RAG query failed", error=str(e))
    return {"answer": "知识库服务暂时不可用，请稍后重试。", "sources": []}
```

**代码精讲 — 降级策略的实现**：

这段代码是"降级策略"的教科书级示例：

1. `try:` — 整个 RAG 调用包裹在 try 块中。任何异常（网络问题、服务崩溃、超时）都不会让 Agent Service 崩溃。

2. `if resp.status_code == 200:` — 只接受 200 的成功响应。如果 RAG 返回 500，不会盲目解析。

3. `except Exception as e:` — 捕获所有异常，记录日志。

4. `return {"answer": "知识库服务暂时不可用...", "sources": []}` — 降级响应！用户不会看到报错，而是看到一条友好的提示信息。

这是"服务容错"的核心思想：**宁可降级服务，不可整体崩溃**。

### 3. httpx 调用的最佳实践对比

在 Agent Service 中可以看到两种 httpx 调用模式：

**模式 1: 内联调用（闲聊处理）**

```python
# 在函数内创建客户端
async with httpx.AsyncClient(timeout=30) as client:
    resp = await client.post(...)
```

优点：代码简洁，适合偶尔的调用
缺点：每次都创建新客户端，浪费了连接复用

**模式 2: 外部传入（未在代码中显式体现，但架构支持）**

```python
# 将 httpx 客户端注入到 Agent 的上下文中
# agent.httpx_client = external_client
```

优点：连接池复用，性能更好
缺点：需要管理客户端生命周期

在当前代码中，使用模式 1（内联）是合理的——每个请求独立，逻辑清晰，不会因共享连接导致意外问题。

### 4. 为什么 Agent Service 是同步等待的？

```python
@app.post("/chat", response_model=ChatResponse)
async def chat(request: ChatRequest):
    intent_result = await intent_classifier.classify(request.message)

    if intent_result.intent_type == IntentType.CHITCHAT:
        answer = await _handle_chitchat(request.message)
        return ChatResponse(session_id=session_id, intent="chitchat", answer=answer)
```

注意用户的请求是 `await _handle_chitchat(message)` —— 同步等待 LLM 返回结果。为什么不让它异步？因为聊天场景下，用户需要一个"完整"的回答，而不是分步通知。

但对于耗时任务（专业计算），采用不同的策略：

```python
elif intent_result.intent_type in (IntentType.TOOL_CALL, IntentType.PROFESSIONAL_TASK):
    task = await task_planner.plan(request.message, intent_result)
    await task_executor.execute_async(task, session_id, request.user_id)
    return ChatResponse(..., task_id=task["task_id"])
```

这里不等待任务完成，而是：
1. 创建任务并获取 `task_id`
2. 立即返回"任务已创建"
3. 用户后续通过 `/task/{task_id}/status` 轮询进度

这体现了"不同场景用不同模式"的设计智慧。

import asyncio

async def call_agent_service(message: str):
    """模拟前端 -> 网关 -> Agent Service 的调用链"""

        )

    """模拟知识库服务调用"""
    async with httpx.AsyncClient(timeout=10) as client:
        try:
            resp = await client.post(
                "http://localhost:8003/rag/query",

            )

        except httpx.ConnectError:

    # 正常调用
    result = await call_agent_service("你好，GrassSea")

### 实践3: 实现一个简单的重试装饰器

```python
import asyncio

def retry_on_failure(max_retries=3, delay=1.0):
    """重试装饰器 — 用于 httpx 调用的容错"""
    def decorator(func):
        async def wrapper(*args, **kwargs):
            last_error = None
            for attempt in range(1, max_retries + 1):
                try:
                    return await func(*args, **kwargs)
                except Exception as e:
                    last_error = e
                    if attempt < max_retries:
                        print(f"重试 {attempt}/{max_retries}，等待 {delay}s...")
                        await asyncio.sleep(delay)
            raise last_error
        return wrapper
    return decorator

@retry_on_failure(max_retries=3, delay=2.0)
async def call_llm_with_retry(message: str):
    async with httpx.AsyncClient(timeout=30) as client:
        resp = await client.post("...", json={...})
        return resp.json()

# 和 GrassSea 中 _propagate_all_secrets 的重试逻辑对比：
# 手动重试循环 vs @retry_on_failure 装饰器，本质相同
# 装饰器更优雅但灵活性稍低（比如想在重试间做不同操作）
```

## 常见问题与排错

### Q1: httpx 调用时出现 ConnectError

**错误信息**: `httpx.ConnectError: [Errno 111] Connection refused`
**原因**: 目标服务未启动或端口错误。
**排查**: 
1. 检查目标服务是否启动: `curl http://localhost:8002/health`
2. 检查端口号是否正确
3. Docker 环境中用服务名而非 localhost

### Q2: httpx.ReadTimeout 超时

**原因**: 目标服务响应太慢。
**解决方案**:
1. 增加 `timeout` 值（如从 30 改为 60）
2. 优化目标服务的处理速度
3. 对于耗时操作，改用异步任务模式（创建任务后用 task_id 轮询）

### Q3: 选择 httpx 还是 requests？

区别是:
- `httpx` 支持 `async/await`，适合 FastAPI 异步环境
- `requests` 是同步库，会阻塞事件循环，**不要在 FastAPI 中用 requests**
- `httpx` 几乎完全兼容 `requests` 的 API，迁移成本很低

### Q4: 什么时候该引入 gRPC？

如果满足以下条件之一：
1. 内部服务之间的调用量超过每秒 1000 次
2. 需要强类型接口契约（protobuf 提供）
3. 需要双向流通信

对于 GrassSea 当前阶段，HTTP/httpx 完全足够。
