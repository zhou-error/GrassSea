## 概念讲解

### 稠密 vs 稀疏：两种"查找"哲学

```
         稠密向量检索 (Dense)              稀疏检索 (Sparse / BM25)
        ─────────────────────            ───────────────────────
原理:    文本 → 向量 → 算距离            文本 → 分词 → 统计匹配

                "舱壁间距"                        "舱壁间距"
                    │                                │
                    ▼                                ▼
            ┌──────────────┐                ┌──────────────┐
            │ [0.2, -0.3,  │                │ 舱壁: 出现在  │
            │  0.8, 0.1...]│                │ doc1,doc2    │
            └──────┬───────┘                │ 间距: 出现在  │
                   │                        │ doc1,doc3    │
                   ▼                        └──────┬───────┘
            ┌──────────────┐                       │
            │ 余弦相似度    │                       ▼
            │ → Top-K 结果  │               ┌──────────────┐
            └──────────────┘               │ BM25 公式    │
                                           │ → Top-K 结果  │
                                           └──────────────┘

擅长:  同义词/近义词匹配               精确词匹配
       "舱壁间距"≈"壁板间隔"          必须包含"舱壁"
       
弱点:  可能漏掉精确术语匹配             不懂同义词
       "§3.2.1"和"第三条"可能           "舱壁"找不到
       相似度不够                         "隔壁"的内容
```

### BM25 是什么？

BM25 是 TF-IDF 的升级版，是搜索引擎的核心算法。公式看起来复杂，但直觉很简单：

```
BM25(query, doc) = Σ IDF(词) × TF(词在doc中的频率) × 归一化

关键概念：
┌─────────────────────────────────────────────────────────────┐
│ TF (Term Frequency)：词在文档中出现了多少次                  │
│   出现越多 → 分数越高（但有上限，防止一个词出现100次就100倍）│
│                                                             │
│ IDF (Inverse Document Frequency)：词在整个文档库中"有多稀有" │
│   "的"出现在几乎所有文档 → IDF 很低 → 对分数贡献很小        │
│   "方型系数"只出现在少量文档 → IDF 很高 → 对分数贡献很大    │
│                                                             │
│ 文档长度归一化：长文档天然包含更多词，需要除以文档长度来公平  │
└─────────────────────────────────────────────────────────────┘
```

### 为什么两路融合比单独一路好？

```
场景：用户问 "CCS 规范中关于散货船舱壁的3.2.1条文内容是什么？"

纯稠密检索：
  找到："舱壁结构设计要求"（语义相关，但不含"3.2.1"）
  漏掉："第3.2.1条 散货船舱壁..."（含精确编号，但向量不够接近）

纯稀疏检索：
  找到："第3.2.1条 散货船舱壁间距要求"（精确匹配"3.2.1"）
  漏掉："散货船横舱壁设计规范"（语义相关但词不同）

混合检索 = 稠密 70% + 稀疏 30%：
  两路结果互补，交叉验证，召回率和精确率都更高
```

### HybridRetriever 架构

```python
class HybridRetriever:
    """混合检索器：稠密向量检索 + BM25 稀疏检索 -> 融合排序"""

    def __init__(self, settings: Settings):
        self.settings = settings
        self.dense_weight = 0.7    # 稠密向量权重
        self.sparse_weight = 0.3   # 稀疏检索权重
        self._bm25_index: dict = {}  # 简易内存 BM25 索引
```

权重 0.7 和 0.3 是怎么确定的？这是工程经验值。一般来说：
- 用户问题偏向**概念性/解释性**时，稠密更重要
- 用户问题偏向**精确术语/编号**时，稀疏更重要

0.7:0.3 是通用文档检索的常用比例。

### 核心方法：hybrid_search

```python
async def hybrid_search(
    self,
    query: str,
    top_k: int = 20,
    knowledge_bases: list[str] | None = None,
) -> list[SearchResult]:
    # 并行执行两路检索
    dense_results = await self._dense_search(query, top_k, knowledge_bases)
    sparse_results = await self._sparse_search(query, top_k, knowledge_bases)

    # 融合分数
    merged = self._merge_results(dense_results, sparse_results)

    # 按融合分数降序排列
    merged.sort(key=lambda x: x.score, reverse=True)

    return merged[:top_k]
```

注意：这里的两路检索是**并行**的（两个 `await` 可以被 `asyncio.gather()` 并发执行，不过当前代码是顺序 await，这是一个可优化点）。

### 稠密检索：_dense_search

```python
async def _dense_search(self, query, top_k, knowledge_bases):
    # 1. 生成查询的 Embedding
    query_embedding = await self._generate_query_embedding(query)

    # 2. Milvus 向量检索
    search_params = {
        "metric_type": "COSINE",
        "params": {"nprobe": 16},  # 搜索的聚类数
    }

    # 3. 构建知识库过滤表达式
    expr = None
    if knowledge_bases:
        kb_conditions = [f'knowledge_base == "{kb}"' for kb in knowledge_bases]
        expr = " or ".join(kb_conditions)
    # 例如：expr = 'knowledge_base == "规范标准库" or knowledge_base == "船舶设计库"'

    # 4. 执行检索
    results = self._collection.search(
        data=[query_embedding],
        anns_field="embedding",     # 在哪个字段上搜
        param=search_params,
        limit=top_k,
        expr=expr,                  # 标量过滤条件
        output_fields=["text", "knowledge_base", "filename", "chunk_index"],
    )
```

**Milvus 的标量过滤（expr）**是实现知识库隔离的关键。它让你在向量检索的同时用 SQL-like 条件过滤，且过滤在索引之前执行，效率很高。

`nprobe=16`：搜索时检查 16 个最近的聚类（总共 128 个）。更大的 nprobe 提高召回率但降低速度。

### 稀疏检索：_sparse_search (BM25)

```python
async def _sparse_search(self, query, top_k, knowledge_bases):
    # 1. 分词（中英文混合）
    tokens = self._tokenize(query)

    # 2. BM25 评分核心参数
    k1 = 1.5   # 词频饱和度参数
    b = 0.75   # 文档长度归一化参数

    # 3. 对每个词，计算它对每个文档的贡献
    for token in tokens:
        posting_list = self._bm25_index.get(token, {})
        # IDF：逆文档频率
        idf = math.log(
            (total_docs - len(posting_list) + 0.5) /
            (len(posting_list) + 0.5) + 1
        )

        for doc_id, tf in posting_list.items():
            doc_len = self._bm25_index.get(f"_len_{doc_id}", avg_dl)
            numerator = tf * (k1 + 1)
            denominator = tf + k1 * (1 - b + b * doc_len / avg_dl)
            scores[doc_id] += idf * numerator / denominator
```

`k1=1.5` 和 `b=0.75` 是 BM25 的经典参数，来自学术界的广泛验证。

### 融合策略：_merge_results

```python
def _merge_results(self, dense, sparse):
    merged: dict[str, SearchResult] = {}

    # 归一化：将两路分数都映射到 [0, 1] 区间
    max_dense = max((r.score for r in dense), default=1.0) or 1.0
    max_sparse = max((r.score for r in sparse), default=1.0) or 1.0

    for r in dense:
        norm_score = r.score / max_dense          # 归一化稠密分数
        merged[r.chunk_id] = SearchResult(
            ..., score=norm_score * self.dense_weight  # x 0.7
        )

    for r in sparse:
        norm_score = r.score / max_sparse         # 归一化稀疏分数
        if r.chunk_id in merged:
            merged[r.chunk_id].score += norm_score * self.sparse_weight  # 累加
        else:
            merged[r.chunk_id] = SearchResult(
                ..., score=norm_score * self.sparse_weight
            )
```

**为什么需要归一化？**

稠密检索的分数是余弦相似度（通常在 0.3-0.9 之间），BM25 的分数范围则取决于查询词数和文档长度（可能从 0 到几十）。如果不归一化，两路分数的量级差异会导致一路完全主导另一路。

### 分词器：_tokenize

```python
def _tokenize(self, text: str) -> list[str]:
    tokens = []
    # 英文词
    tokens.extend(re.findall(r"[a-zA-Z]+", text.lower()))
    # 中文二字词组（最简单的 bigram）
    chinese = re.findall(r"[一-鿿]", text)
    for i in range(len(chinese) - 1):
        tokens.append(chinese[i] + chinese[i + 1])
    # 中文单字
    tokens.extend(chinese)
    # 数字
    tokens.extend(re.findall(r"\d+", text))
    return tokens
```

这是一个**简易分词器**。生产环境应该使用专业分词库（如 jieba 对中文），但简易版本足以理解原理。例如：

```
输入: "散货船舱壁间距600mm"
输出: ["散货", "货船", "船舱", "舱壁", "壁间", "间距", 
       "散", "货", "船", "舱", "壁", "间", "距",
       "600"]
```

## 手把手实践

### 实验一：手算 BM25

```python
# bm25_demo.py -- 理解 BM25 计算
import math

# 假设有3篇文档
docs = {
    "doc1": "散货船舱壁间距要求不小于600mm",
    "doc2": "油船舱壁结构设计规范",
    "doc3": "散货船横舱壁间距的计算方法",
}

# 计算 IDF（针对词"舱壁"）
docs_with_word = 3  # "舱壁"在3个文档中都出现
total_docs = 3
idf = math.log((total_docs - docs_with_word + 0.5) / (docs_with_word + 0.5) + 1)
print(f"'舱壁'的 IDF: {idf:.3f}")  # 很低，因为太常见

# 计算 IDF（针对词"600mm"）
docs_with_word = 1  # 只在doc1中出现
idf = math.log((total_docs - docs_with_word + 0.5) / (docs_with_word + 0.5) + 1)
print(f"'600mm'的 IDF: {idf:.3f}")  # 较高，因为稀有
```

你会发现："舱壁"的 IDF 很低（遍地都是），"600mm"的 IDF 更高（能区分文档）。这就是 IDF 的核心价值。

### 实验二：观察归一化的重要性

```python
# normalization_demo.py
dense_scores = [0.85, 0.72, 0.68, 0.55, 0.41]
sparse_scores = [12.5, 8.3, 6.1, 4.2, 2.8]

# 不归一化直接相加
raw = [d + s for d, s in zip(dense_scores, sparse_scores)]
print("未归一化:", raw)  # 稀疏主导

# 归一化后相加
dense_norm = [d / max(dense_scores) for d in dense_scores]
sparse_norm = [s / max(sparse_scores) for s in sparse_scores]
normalized = [d * 0.7 + s * 0.3 for d, s in zip(dense_norm, sparse_norm)]
print("归一化:", normalized)  # 平衡
```

## 常见问题与排错

**Q1：BM25 索引什么时候构建？**

A：当前代码中的 `_bm25_index` 是空的——这是简化实现。生产环境中，每次文档索引完成后应同步更新 BM25 倒排索引。一个典型做法是在 `_insert_to_milvus` 之后调用 `_update_bm25_index(chunks)`。

**Q2：稠密和稀疏的权重 0.7/0.3 是固定的，能根据查询动态调整吗？**

A：可以！一个进阶方案是让意图识别模块参与决策：
- 识别到"精确查询"（如条文编号）时，增加稀疏权重
- 识别到"概念查询"（如"什么是稳性"）时，增加稠密权重

这在 GrassSea 的未来迭代中可以实现。

**Q3：为什么 _dense_search 和 _sparse_search 返回类型不一致？**

A：它们都返回 `list[SearchResult]`，类型是一致的。区别在于 score 字段的值域不同，这正是 `_merge_results` 需要归一化的原因。
