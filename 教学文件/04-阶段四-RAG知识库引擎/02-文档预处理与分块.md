## 概念讲解

### 为什么需要分块（Chunking）？

直接给大模型塞一整本书是不行的。原因有三：

```
问题一：Token 限制
┌──────────────────────────────────────────┐
│ LLM 有上下文窗口限制（如 DeepSeek-V3 是   │
│ 128K tokens）。一本 CCS 规范可能超过      │
│ 百万 token，根本塞不进去。                │
└──────────────────────────────────────────┘

问题二：检索精度
┌──────────────────────────────────────────┐
│ 如果以整篇文档为单位做检索，向量表达的    │
│ 是"整本书讲什么"，而不是"书的第几章第几页  │
│ 在讲散货船舱壁"。粒度太粗，检索不准。     │
└──────────────────────────────────────────┘

问题三：生成质量
┌──────────────────────────────────────────┐
│ LLM 处理的信息越多，越容易丢失重点。      │
│ 给它3个精准的段落，比给它30页文档效果更好。│
└──────────────────────────────────────────┘
```

### chunk_size 和 chunk_overlap 是什么？

```
原文：AAAA BBBB CCCC DDDD EEEE FFFF GGGG HHHH

chunk_size=4, overlap=1 的分块效果：

Chunk 1: [AAAA BBBB CCCC DDDD]
              └──overlap──┘
Chunk 2:         [DDDD EEEE FFFF GGGG]
                       └──overlap──┘
Chunk 3:              [GGGG HHHH .... ....]
```

- **chunk_size**：每个分块包含多少 token（GrassSea 中使用 512）
- **chunk_overlap**：相邻分块之间重叠多少 token（GrassSea 中使用 64）

**为什么需要 overlap（重叠）？**

想象你在分块时恰好把一个重要的定义从中间切断了：

```
原文："根据 CCS 规范，散货船舱壁间距应不小于 600mm。"

如果没有 overlap，可能被切成：
  Chunk A: "根据 CCS 规范，散货船舱壁"
  Chunk B: "间距应不小于 600mm。"

检索 "舱壁间距要求" 时，Chunk B 能匹配到，但 Chunk B 脱离了上下文
（不知道是 CCS 规范还是别的什么规范）。

有了 overlap：
  Chunk A: "根据 CCS 规范，散货船舱壁间距应"
  Chunk B: "散货船舱壁间距应不小于 600mm。"
此时两个 chunk 都包含了完整的语义。
```

### Semantic Chunking（语义分块）vs 固定长度分块

```
固定长度分块（Naive）：
┌──────────┬──────────┬──────────┬──────────┐
│ chunk_0  │ chunk_1  │ chunk_2  │ chunk_3  │  ← 每512字一刀切
└──────────┴──────────┴──────────┴──────────┘
  可能切断句子甚至词语

语义分块（Semantic）：
┌─────────────┬──────────────┬──────────┬───────────────┐
│  第1章 概述  │  第2章 稳性   │ 第2.1节  │  第2.2节 ...  │  ← 按段落/章节边界
└─────────────┴──────────────┴──────────┴───────────────┘
  保持语义完整性
```

GrassSea 的策略是**优先按段落自然边界**切分，只有在段落太长时才在段落内拆分。

### 整体架构：DocumentIngestionPipeline

```python
class DocumentIngestionPipeline:
    """文档预处理流水线
    步骤：解析 -> 清洗 -> 分块 -> 向量化 -> 索引
    """

    def __init__(self, settings: Settings):
        self.chunk_size = 512     # 每个分块的最大 token 数
        self.chunk_overlap = 64   # 相邻分块的重叠 token 数
```

这两个参数值的选择有讲究：
- **512 tokens**：适合大多数 embedding 模型的输入限制，也是信息密度和检索精度之间的平衡点
- **64 tokens**：约等于 chunk_size 的 12.5%，能在保证语义连贯的同时不致冗余

### 主流程：process_and_index

```python
async def process_and_index(
    self,
    document_id: str,
    filename: str,
    content: bytes,          # 文件原始二进制内容
    content_type: str,       # "pdf" / "txt" / "md"
    knowledge_base: str = "项目知识库",
) -> int:
    # Step 1: 解析文档为纯文本
    text = await self._parse_document(content, content_type)

    # Step 2: 文本清洗
    text = self._clean_text(text)

    # Step 3: 语义分块
    chunks = self._chunk_text(
        text,
        chunk_size=self.chunk_size,
        chunk_overlap=self.chunk_overlap,
        document_id=document_id,
        filename=filename,
        knowledge_base=knowledge_base,
    )

    # Step 4: 向量化并写入 Milvus
    await self._index_chunks(chunks)

    return len(chunks)
```

**逐步解析**：

**Step 1 - 文档解析**：将各种格式统一转换为纯文本。

```python
async def _parse_document(self, content: bytes, content_type: str) -> str:
    if content_type == "txt":
        return content.decode("utf-8", errors="replace")

    elif content_type in ("md", "markdown"):
        return content.decode("utf-8", errors="replace")

    elif content_type == "pdf":
        return await self._parse_pdf(content)
```

`errors="replace"` 很重要：UTF-8 解码遇到非法字节时，用替换字符替代而不是直接崩溃。这是生产代码的防御性编程习惯。

PDF 解析使用了 PyMuPDF（fitz）作为主解析器，PyPDF2 作为备选：

```python
async def _parse_pdf(self, content: bytes) -> str:
    try:
        import fitz  # PyMuPDF -- 性能更好，支持更多格式
        doc = fitz.open(stream=content, filetype="pdf")
        text_parts = []
        for page in doc:
            text_parts.append(page.get_text("text", flags=fitz.TEXT_PRESERVE_WHITESPACE))
        doc.close()
        return "\n\n".join(text_parts)
    except ImportError:
        # 降级：PyPDF2 是纯 Python 实现，安装更简单
        from PyPDF2 import PdfReader
        # ... 类似逻辑
```

**Step 2 - 文本清洗**：去除多余的空白、空行、格式噪声。

```python
def _clean_text(self, text: str) -> str:
    text = re.sub(r"\n{4,}", "\n\n\n", text)   # 4个以上换行合并为3个
    text = re.sub(r"[ \t]{3,}", "  ", text)     # 3个以上空格合并为2个
    text = text.strip()                         # 去除首尾空白
    return text
```

为什么不全合并成1个换行？因为 PDF 解析出来的多换行通常代表章节分界，保留一定程度的空白有助于后续分块时识别自然边界。

### 核心：语义分块逻辑

```python
def _chunk_text(self, text, chunk_size, chunk_overlap, ...):
    # 1. 按段落（双换行）切分
    paragraphs = re.split(r"\n\n+", text)

    current_chunk = ""
    chunk_index = 0

    for para in paragraphs:
        para = para.strip()
        if not para:
            continue

        # 2. 判断加入当前段落后是否超出限制
        if len(current_chunk) + len(para) > chunk_size * 2.5:
            # 超出限制：保存当前 chunk，开始新 chunk
            if current_chunk:
                chunks.append(DocumentChunk(...))
                chunk_index += 1
                # 从当前 chunk 末尾截取 overlap 部分作为新 chunk 的开头
                overlap_text = current_chunk[-int(chunk_overlap * 2.5):]
                current_chunk = overlap_text + "\n\n" + para
        else:
            # 未超出：继续追加
            current_chunk += "\n\n" + para

    # 3. 保存最后一个 chunk
    if current_chunk.strip():
        chunks.append(DocumentChunk(...))
```

**关键细节**：代码中使用 `chunk_size * 2.5` 进行字符数估算。为什么是 2.5？

```
中英文 token 估算：
- 英文：1 token ≈ 4 个字符（包括空格）
- 中文：1 token ≈ 1.5-2 个汉字

取中值：1 token ≈ 2.5 个字符
所以 chunk_size=512 tokens ≈ 1280 个字符

这是一个经验估算，实际 token 数由 embedding 模型的 tokenizer 决定。
```

### DocumentChunk 数据结构

```python
class DocumentChunk:
    def __init__(self, chunk_id, text, metadata, chunk_index):
        self.chunk_id = chunk_id        # "doc_abc123_chunk_5"
        self.text = text                # 文本内容
        self.metadata = metadata        # {"document_id", "filename", "knowledge_base"}
        self.chunk_index = chunk_index  # 在原文档中的位置序号
```

metadata 中保存了三个关键信息：
- **knowledge_base**：所属知识库（如"规范标准库"），供检索时过滤使用
- **filename**：源文件名，供生成回答时标注来源
- **chunk_index**：在原文档中的序号，供精确定位引用位置

## 手把手实践

### 实验一：自己实现一个简易分块器

```python
# simple_chunker.py -- 10行代码理解分块原理
def simple_chunk(text, chunk_size=100, overlap=20):
    chunks = []
    start = 0
    idx = 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append({
            "chunk_id": f"chunk_{idx}",
            "text": text[start:end],
            "chunk_index": idx,
        })
        start = end - overlap  # 下一个chunk的起点 = 当前位置 - overlap
        idx += 1
    return chunks

# 测试
text = "RAG是检索增强生成的缩写。它的核心思想是先检索相关文档，再基于文档生成回答。这种方法的优势在于可以引用具体来源。"
chunks = simple_chunk(text, chunk_size=30, overlap=10)
for c in chunks:
    print(f"{c['chunk_id']}: {c['text']}")
```

运行这段代码，观察 overlap 如何让相邻 chunk 之间产生重叠。

### 实验二：对比固定分块和语义分块

准备一段带有分节标题的文本（如一篇论文），分别用以下两种方法分块：

## 常见问题与排错

**Q1：chunk_size 设多大最合适？**

A：没有万能的最佳值。参考经验：
- 通用场景：256-512 tokens
- 需要精确匹配的条文/规范：128-256 tokens
- 需要理解上下文的综述/报告：512-1024 tokens

GrassSea 选择 512 是因为船舶规范条文通常较长，需要足够的上下文。

**Q2：PDF 解析出来是乱码怎么办？**

A：PDF 的文本提取取决于文档的生成方式：
- 文字型 PDF（Word 导出等）：PyMuPDF 通常能正常提取
- 扫描型 PDF（图片转PDF）：需要 OCR 引擎（如 PaddleOCR）
- 加密 PDF：需要先解密

如果 PyMuPDF 失败，代码中的降级策略（PyPDF2）可能也帮不上忙，此时需要引入 OCR。

**Q3：为什么 metadata 放在 chunk 里而不是单独存一张表？**

A：这是权衡的结果。好处是检索时随手可得，不需要 JOIN 查询；代价是存储空间稍大。对于知识库检索这种读多写少的场景，优先保证读取速度是合理的选择。
