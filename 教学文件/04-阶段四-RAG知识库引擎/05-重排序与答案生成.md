## 概念讲解

### 为什么需要重排序？

检索阶段返回 20 条候选结果，但排序的依据是"向量相似度"——这不够精确。

```
Example: 用户问 "GM值的安全范围是多少？"

检索 Top-3 (按余弦相似度):
  1. "GM值的定义：稳心与重心的垂直距离..."        相似度 0.89
  2. "IMO规定客船GM值应不小于0.15m..."           相似度 0.87
  3. "GM是General Motors的缩写，是美国汽车公司..." 相似度 0.86

重排序后 (按 Cross-encoder 判断"是否能回答问题"):
  1. "IMO规定客船GM值应不小于0.15m..."           分数 0.95
  2. "GM值的定义：稳心与重心的垂直距离..."        分数 0.78
  3. "GM是General Motors的缩写..."              分数 0.02
```

第3条"GM是通用汽车"的向量和问题确实有点相似（因为都有"GM"这个词），但 Cross-encoder 同时读入问题和段落后能判断"这和船舶完全无关"，给出极低分数。

### Bi-encoder vs Cross-encoder

```
Bi-encoder（双塔模型）-- 检索阶段使用
═══════════════════════════════════════════
        问题                    文档
         │                       │
         ▼                       ▼
    ┌─────────┐            ┌─────────┐
    │Encoder Q│            │Encoder D│   ← 分别编码
    └────┬────┘            └────┬────┘
         │  向量              │ 向量
         └───── 算相似度 ─────┘
                ↑
         快速，可预计算文档向量
         但问题-文档没有真正"见面"


Cross-encoder（交叉编码模型）-- 重排序使用
═══════════════════════════════════════════
     问题 + 文档
         │
         ▼
    ┌─────────────────────┐
    │   Cross-Encoder     │   ← 一起输入
    │ (问题, 文档) → 分数  │
    └─────────┬───────────┘
              │
           分数
              ↑
       精准，但慢（每对都要算一次）
       只对 Top-K 候选使用
```

GrassSea 的策略：Bi-encoder 快速召回 20 条 -> Cross-encoder 精准排序 Top-5。

### Prompt 模板设计原则

给 LLM 写 Prompt 就像给实习生写工作指引：

```
坏的 Prompt：
"回答问题"
→ LLM 可能任意发挥，甚至编造

好的 Prompt：
"你是专业助手。回答必须基于参考资料。
 每个论断标注来源。信息不足时说明。
 使用专业术语。用 Markdown 组织。"
→ LLM 行为可预测，输出质量可控
```

### 重排序器：reranker.py

打开 `services/knowledge_service/reranker.py`。

```python
class Reranker:
    """Cross-encoder 重排序器"""

    def __init__(self, model_name: str = "BAAI/bge-reranker-v2-m3"):
        self.model_name = model_name
        self._model = None
        self._tokenizer = None
```

`bge-reranker-v2-m3` 是 BAAI（北京智源研究院）发布的 Cross-encoder 模型，在中文检索任务上表现优异。它是开源模型，可以本地部署。

**延迟加载模式**：

```python
async def _ensure_model(self):
    """延迟加载模型 -- 只在第一次使用时才加载"""
    if self._model is not None:
        return
    try:
        from transformers import AutoModelForSequenceClassification, AutoTokenizer
        self._tokenizer = AutoTokenizer.from_pretrained(self.model_name)
        self._model = AutoModelForSequenceClassification.from_pretrained(self.model_name)
        self._model.eval()  # 评估模式（不计算梯度，省显存）
        logger.info("Reranker model loaded")
    except ImportError:
        logger.warning("transformers not installed, using fallback")
    except Exception as e:
        logger.warning("Failed to load reranker model, using fallback")
```

为什么用延迟加载而不是在 `__init__` 中加载？
1. **启动速度**：加载模型需要数秒甚至数十秒，延迟加载让服务先启动
2. **资源节省**：如果一直不需要重排序，模型就不会被加载
3. **优雅降级**：加载失败时自动切换到简单的分数排序

### Cross-encoder 推理

```python
async def _cross_encoder_rerank(self, query, candidates, top_k):
    await self._ensure_model()

    # 构造 (问题, 段落) 对
    pairs = [[query, c.text] for c in candidates]

    scores = []
    with torch.no_grad():  # 禁用梯度计算，节省显存和加速推理
        for pair in pairs:
            inputs = self._tokenizer(
                pair[0], pair[1],
                max_length=512,       # 截断长度
                truncation=True,
                padding=True,
                return_tensors="pt",  # PyTorch 张量
            )
            outputs = self._model(**inputs)
            score = outputs.logits.squeeze().item()
            scores.append(score)

    # 更新分数并排序
    for candidate, score in zip(candidates, scores):
        candidate.score = score
    candidates.sort(key=lambda x: x.score, reverse=True)
    return candidates[:top_k]
```

`torch.no_grad()` 是关键：推理不需要梯度（只有训练需要），禁用后显存占用减半，速度翻倍。

这个 Prompt 设计遵循了三个原则：
1. **角色设定**（第1行）：告诉 LLM 它是谁
2. **行为约束**（规则1-5）：告诉 LLM 能做什么、不能做什么
3. **输出格式**（规则2+5）：告诉 LLM 怎么输出

### 上下文格式化

```python
def _format_contexts(self, contexts: list[str], sources: list) -> str:
    formatted = []
    for i, (ctx, src) in enumerate(zip(contexts, sources)):
        kb = getattr(src, "source", {}).get("knowledge_base", "未知库")
        filename = getattr(src, "source", {}).get("filename", "未知文档")
        chunk_idx = getattr(src, "chunk_index", i)

        formatted.append(
            f"### 参考资料 {i + 1}\n"
            f"**来源**: {filename}（{kb}）\n"
            f"**位置**: chunk_{chunk_idx}\n"
            f"**内容**:\n{ctx}\n"
        )
    return "\n---\n".join(formatted)
```

这段代码将检索结果格式化成 LLM 能"看懂"的参考资料格式：


### LLM 调用与降级

```python
async def _call_llm(self, messages: list[dict]) -> str:
    # 优先使用 DeepSeek API
    if self.settings.DEEPSEEK_API_KEY:
        try:
            response = await client.post(

                json={
                    "model": "deepseek-chat",
                    "messages": messages,
                    "temperature": 0.3,     # 低温度 = 更确定性、更少幻觉
                    "max_tokens": 2048,
                },
            )
            return data["choices"][0]["message"]["content"]
        except Exception as e:
            logger.error("LLM call failed, using fallback")

    # Fallback: 直接返回检索结果摘要
    return self._fallback_answer(messages)
```

**temperature=0.3** 的选择：
- temperature=0：完全确定性（每次输出一样），但可能过于死板
- temperature=1.0：创造性高，但可能跑偏、编造
- temperature=0.3：在确定性和灵活性之间的平衡，适合"基于事实回答"的场景

**降级策略**：

```python
def _fallback_answer(self, messages):
    return (
        "## 参考资料摘要（离线模式）\n\n"
        "当前未配置 LLM API Key，无法生成完整的回答。"
        "以下是检索到的相关参考资料：\n\n"
        f"{user_content}\n\n"
        "---\n"
        "请配置 DEEPSEEK_API_KEY 环境变量以启用完整功能。"
    )
```

降级策略的目标是：**即使 LLM 不可用，用户也能看到检索到的原始资料**。这是一种用户体验保护机制，而不是直接返回 500 错误。

```python
# temperature_demo.py -- 理解 temperature 参数

questions = [
```

观察：temperature 越高，同一个问题每次回答的用词和结构差异越大。对于"事实性问题"（如规范条文），低 temperature 更合适；对于"开放性问题"（如设计建议），可以适当提高。

## 常见问题与排错

**Q1：bge-reranker 模型下载失败怎么办？**

A：模型文件约 2GB，需要稳定的网络。可以：
1. 设置 HuggingFace 镜像：`export HF_ENDPOINT=https://hf-mirror.com`
2. 手动下载模型文件放到 `~/.cache/huggingface/hub/`
3. 模型加载失败时会自动降级到分数排序

**Q2：为什么不在检索阶段直接使用 Cross-encoder？**

A：因为太慢了。对 10 万条文档每条都和问题做一次 Cross-encoder 推理需要数分钟。而先做 Bi-encoder 快速召回 20 条，再对 20 条做 Cross-encoder，总时间不到 1 秒。

**Q3：`_format_contexts` 中为什么用 `getattr(src, "source", {}).get(...)` 而不是 `src.source.get(...)`？**

A：`getattr` 与 `.get()` 的三层嵌套是一种防御性编程策略，当数据结构的任何一层缺失或为 None 时都不会崩溃。这是处理外部数据（API 返回、用户输入）的常见模式。
