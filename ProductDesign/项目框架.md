## 1. 设计总览

### 1.1 系统定位与目标用户

白草沧智（GrassSea AI）是一个面向**船舶与海洋工程**领域的 AI 原生多智能体协作平台。系统以"大语言模型（LLM）+ 专业知识库 + 多智能体编排 + 专业工具链"为核心，为船舶行业的全生命周期（概念设计、详细设计、建造、运维）提供智能化支持。

**目标用户群体**：

| 用户角色 | 典型使用场景 | 核心需求 |
|---------|------------|---------|
| 船舶设计师 | 型线设计、规范审查、性能计算 | CAD 集成、合规性自动检查、多方案对比 |
| 船舶工程师 | 结构计算、图纸绘制、技术报告 | 参数化建模、规范溯源、报告自动生成 |
| 船舶研究人员 | 文献调研、数据分析、模型试验 | 知识检索、每日简报、仿真计算 |
| 项目经理 | 任务分配、进度跟踪、文档管理 | 子代理编排、待办管理、统计看板 |
| 嵌入式/电气工程师 | 船舶电气系统、自动化硬件开发 | 代码生成、接口对接、硬件调试支持 |

### 1.2 设计原则

| 原则 | 说明 | 落地方式 |
|------|------|---------|
| **模块化（Modularity）** | 各层职责明确，接口标准化 | 分层架构 + 统一 API 协议 + 依赖注入 |
| **可扩展（Extensibility）** | 工具、智能体、知识库均可热插拔 | 插件注册机制 + 统一工具接口规范 |
| **安全优先（Security-first）** | 数据隔离、权限控制、传输加密 | RBAC + TLS + 项目级知识库隔离 |
| **实时响应（Real-time）** | 简单对话秒级响应，复杂任务异步推送 | WebSocket + 消息队列 + 流式输出 |
| **可观测（Observability）** | 全链路追踪、用量统计、异常告警 | OpenTelemetry + 时序指标 + 日志中心 |
| **专业可靠（Domain-reliable）** | 船舶专业输出可溯源、可验证 | 知识图谱 + 规范条文溯源 + 人工复核通道 |

## 2. 分层架构详细设计

### 2.1 多端交互层

#### 2.1.1 支持的终端类型

| 终端类型 | 技术栈 | 适用场景 | 优先级 |
|---------|-------|---------|-------|
| **Web 客户端（SPA）** | React 18 + TypeScript + Ant Design | 主力交互界面，功能全覆盖 | P0 |
| **桌面客户端** | Electron / Tauri | 需要本地文件系统访问、离线能力的场景 | P1 |
| **移动端 App** | React Native / Flutter | 轻量查阅、消息推送、待办提醒 | P2 |
| **第三方 API 接入** | RESTful / gRPC API | 外部系统集成（CAD 软件、PLM 系统） | P1 |
| **IDE 插件** | VS Code Extension / JetBrains Plugin | 开发人员代码辅助 | P2 |
| **CLI 工具** | Python Click / Go Cobra | 自动化脚本、批量处理 | P2 |

#### 2.1.2 统一接入网关（API Gateway）

选用 **Kong Gateway 3.x** 或 **APISIX**，承担以下职责：

- **认证鉴权**：JWT Token 校验，OAuth2.0 集成，API Key 管理
- **流量控制**：基于用户/API/时间的多维度限流（令牌桶算法）
- **路由转发**：根据请求路径将流量分发至对应后端微服务
- **协议转换**：HTTP ↔ WebSocket ↔ gRPC 协议适配
- **请求聚合**：将多个后端接口的数据聚合成一个响应（BFF 模式）
- **日志与监控**：请求日志采集，延迟统计，错误率告警

**推荐理由**：Kong/APISIX 均为云原生网关，插件生态丰富，支持声明式配置和动态更新，适合中小团队快速部署。

#### 2.1.3 协议选择及使用场景

| 协议 | 使用场景 | 优势 | 备注 |
|------|---------|------|------|
| **WebSocket** | 实时对话流式输出、任务进度推送、协同编辑 | 全双工、低延迟、服务端主动推送 | 主要对话通道 |
| **RESTful HTTP/2** | CRUD 操作、文件上传下载、配置管理 | 通用性强、缓存友好、调试方便 | 常规 API |
| **gRPC** | 内部微服务间高性能调用（如 RAG 检索、仿真计算调度） | 二进制协议、强类型、支持流式 | 内部服务通信 |
| **Server-Sent Events (SSE)** | 单向流式推送（如 Token 统计实时更新） | 实现简单、HTTP 原生支持 | 降级方案 |
| **MQTT** | 移动端弱网环境消息推送 | 轻量、省电、QoS 分级 | 移动端备用 |

#### 2.1.4 前端状态管理与离线缓存策略

**状态管理方案**：

```
┌─────────────────────────────────────┐
│          Global State (Zustand)      │
│  ┌─────────┐ ┌─────────┐ ┌───────┐  │
│  │ Auth    │ │ Session │ │ UI    │  │
│  │ Store   │ │ Store   │ │ Store │  │
│  └─────────┘ └─────────┘ └───────┘  │
├─────────────────────────────────────┤
│     Server State (TanStack Query)    │
│  ┌─────────────────────────────────┐ │
│  │  Cache · Refetch · Optimistic   │ │
│  │  Update · Pagination            │ │
│  └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

- **全局状态**：使用 **Zustand**（轻量、无 boilerplate、支持持久化中间件）
- **服务端状态**：使用 **TanStack Query（React Query）** 管理缓存、自动刷新、乐观更新
- **本地持久化**：关键用户设置和草稿使用 `IndexedDB`（通过 Dexie.js），会话 Token 使用 `localStorage`

**离线缓存策略**：

| 场景 | 策略 | 实现 |
|------|------|------|
| 知识库文档浏览 | 最近访问文档缓存到 IndexedDB | Service Worker + Cache API |
| 对话草稿 | 本地暂存，联网后同步 | IndexedDB + 乐观更新 |
| 静态资源 | 预缓存 Shell，运行时缓存内容 | Workbox (PWA) |
| 图片/图纸预览 | LRU 缓存，上限 500MB | IndexedDB 分块存储 |

### 2.2 智能体编排层

#### 2.2.1 意图识别模块（Intent Parser）

**分类体系**：

```
用户输入
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│                    意图分类器（Intent Classifier）          │
│             基于 LLM + 规则引擎的混合分类                    │
├────────────┬──────────┬──────────┬───────────┬───────────┤
│ 闲聊/寒暄   │ 知识查询   │ 工具调用   │ 专业任务    │ 子代理编排  │
│ Chitchat   │ Knowledge │ Tool     │ Professional│ Sub-Agent │
│            │ Query     │ Call     │ Task        │ Orch.     │
├────────────┼──────────┼──────────┼───────────┼───────────┤
│ 简单问候    │ 规范条文   │ 生成报告   │ 稳性计算    │ 多专业联合  │
│ 帮助说明    │ 术语解释   │ 导出PDF   │ 型线绘制    │ 设计任务    │
│ 反馈收集    │ 历史项目   │ CAD操作   │ 规范审查    │ 研究+报告   │
│            │ 文献检索   │ 数据查询   │ 船型改造    │ 图纸+计算   │
└────────────┴──────────┴──────────┴───────────┴───────────┘
```

**混合分类策略**：
1. **快速规则层**（< 50ms）：关键词/正则匹配，覆盖 70% 的常见意图（如"画型线图"、"生成报告"）
2. **LLM 语义层**（200-500ms）：处理复杂/模糊意图，使用分类专用小模型（如 DeepSeek-V3 轻量版）
3. **置信度阈值**：规则命中且置信度 > 0.85 直接路由；否则递升到 LLM 层；两者均低于阈值时主动向用户发起澄清问询

#### 2.2.2 任务规划模块（Task Planner）

**任务拆解策略**：

| 策略 | 适用场景 | 说明 |
|------|---------|------|
| **DAG（有向无环图）** | 多步骤依赖任务（如规范审查 → 标注不合规 → 生成报告） | 明确依赖关系，支持并行 |
| **动态规划** | 计算/优化类任务（如船型改造的迭代优化） | 根据中间结果动态调整后续步骤 |
| **树形分解** | 层级化任务（如完整船舶设计） | 自顶向下逐级细化 |

**DAG 任务图示例**（规范审查 + 图纸绘制联合任务）：

```
                    ┌─────────────┐
                    │  接收设计参数  │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
       ┌──────────┐ ┌──────────┐ ┌──────────┐
       │ 参数完整性 │ │ 规范条文   │ │ 型值表    │
       │   检查    │ │   检索    │ │   解析    │
       └────┬─────┘ └────┬─────┘ └────┬─────┘
            │            │            │
            └────────────┼────────────┘
                         │
                         ▼
                  ┌──────────────┐
                  │   并行执行     │
                  └──────┬───────┘
              ┌──────────┴──────────┐
              ▼                     ▼
       ┌──────────┐          ┌──────────┐
       │ 规范合规性 │          │ 型线图    │
       │   审查    │          │   绘制    │
       └────┬─────┘          └────┬─────┘
            │                     │
            └──────────┬──────────┘
                       ▼
                ┌──────────────┐
                │   结果聚合     │
                └──────┬───────┘

                ┌──────────────┐
                │ 综合报告生成   │

**规划器实现**：
- 采用 **ReAct（Reasoning + Acting）** 模式 + **Chain-of-Thought** 提示
- 每个步骤输出标准格式：`{step_id, action, inputs, expected_outputs, dependencies, timeout}`
- 执行引擎按 DAG 拓扑顺序调度，支持步骤级重试和回滚

#### 2.2.3 多智能体协同机制

**协同架构**：

```
┌─────────────────────────────────────────────────────┐
│                  智能体协同总线（Agent Bus）            │
│                                                       │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────┐ │
│  │ 注册中心(Nacos)│  │ 消息队列(Kafka)│  │事件总线(RabbitMQ)│ │
│  │Service Registry│ │Task Dispatch │  │Event Bus   │ │
│  └──────┬───────┘  └──────┬───────┘  └─────┬──────┘ │
│         │                 │                 │         │
│         └─────────────────┼─────────────────┘         │
│                           │                           │
│  ┌────────────────────────┴────────────────────────┐  │
│  │              Agent gRPC 通信层                    │  │
│  │   统一消息格式: {agent_id, task_id, action,       │  │
│  │                  payload, context, priority}      │  │
│  └─────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

**通信协议选择**：

| 组件 | 选型 | 推荐理由 |
|------|------|---------|
| **注册中心** | Nacos 2.x | 支持服务发现+配置管理，Python SDK 成熟，阿里系生态 |
| **任务调度** | Celery + Redis / RabbitMQ | Python 生态首选，支持优先级、重试、定时任务 |
| **事件总线** | RabbitMQ 3.x | 可靠性高于 Kafka 在低吞吐场景，支持复杂路由（topic/exchange） |
| **Agent 间 RPC** | gRPC (protobuf) | 强类型契约、高性能、跨语言支持 |

> **选型说明**：选择 RabbitMQ 而非 Kafka 作为主要事件总线，因为项目初期日活 < 500、并发量不高。RabbitMQ 的灵活路由（topic exchange）、死信队列、消息确认机制更适合多智能体协同的复杂路由场景。后续当数据流水线（日志采集、流处理）吞吐量增长时，再引入 Kafka 专门处理日志流。

**冲突解决与优先级管理**：

```
任务优先级定义（P0 ~ P3）：
┌────────┬────────────┬──────────────────────────┐
│ 优先级  │ 标签        │ 示例                      │
├────────┼────────────┼──────────────────────────┤
│ P0     │ 紧急/安全   │ 用户取消操作、系统异常告警    │
│ P1     │ 交互实时    │ 用户对话响应、即时工具调用     │
│ P2     │ 批量任务    │ 每日调研报告生成、批量文件处理  │
│ P3     │ 后台维护    │ 知识库索引更新、日志归档      │
└────────┴────────────┴──────────────────────────┘

冲突解决策略：
1. 优先级抢占：P0 可中断 P2/P3 任务
2. 资源预留：对话响应预留 30% LLM 调用配额
3. 死锁检测：DAG 循环依赖检测 + 步骤级超时（默认 300s）
4. 乐观并发：多个 Agent 可并行读取共享知识库，写入采用乐观锁
```

**状态迁移条件**：

| 源状态 → 目标状态 | 触发条件 | 超时处理 |
|------------------|---------|---------|
| IDLE → PARSING | 用户发送消息 | — |
| PARSING → CHITCHAT | 意图分类为闲聊 | PARSING 超时 5s → 默认降级为 CHITCHAT |
| PARSING → KNOWLEDGE | 意图分类为知识查询 | 同上 |
| PARSING → TOOL/TASK | 意图分类为工具调用或专业任务 | 同上 |
| PLANNING → EXECUTING | 任务 DAG 构建完成 | PLANNING 超时 30s → 降级为简单工具调用 |
| EXECUTING → WAITING_USER | 数据不足需补充 | EXECUTING 步骤超时 300s → 标记失败 |
| WAITING_USER → EXECUTING | 用户补充信息 | WAITING_USER 超时 30min → 归档 |
| STREAMING → COMPLETED | 流式输出完毕 | — |
| 任意 → ERROR | 未捕获异常 | 自动重试 1 次，再失败则通知用户 |

class BaseAgent(Protocol):

**检索增强生成流水线**：

```
                        RAG Pipeline
═══════════════════════════════════════════════════════════

┌──────────────┐    ┌──────────────┐    ┌──────────────┐

└──────────────┘    └──────────────┘    └──────────────┘

**检索策略详解**：

| 阶段 | 方法 | 实现细节 |
|------|------|---------|
| **文档预处理** | 智能分块（Semantic Chunking） | 按段落/章节自然边界切分，chunk_size=512 tokens，overlap=64 tokens；表格和公式单独标记 |
| **向量化** | 双路 Embedding | 稠密向量：text-embedding-3-large（通用语义）；稀疏向量：BM25（关键词精确匹配） |
| **混合检索** | 稠密 + 稀疏融合 | 稠密向量相似度（cosine）× 0.7 + BM25 分数 × 0.3；向量数据库 Milvus 2.x 原生支持混合检索 |
| **重排序** | Cross-encoder Reranker | 使用 bge-reranker-v2-m3 对 Top-20 候选重排序，输出 Top-5 |
| **上下文融合** | 引用注入 + 来源标注 | 将检索结果按相关性降序拼接，每条附 `[来源: 文档名, §章节, P页码]` |
| **答案生成** | LLM 带约束生成 | Prompt 模板注入："基于以下参考资料回答，不得编造。若信息不足，明确说明。" |

**仿真引擎设计要点**：

- **统一适配器模式**：每种外部求解器实现统一的 `SolverAdapter` 接口（`setup → run → collect → validate`）
- **结果缓存**：相同输入参数的计算结果缓存至 Redis（TTL 24h），避免重复计算
- **进度推送**：长时仿真（> 10s）通过 WebSocket 实时推送进度百分比
- **输入校验**：计算前自动校验数据完整性（必要参数、单位、范围），数据不足时生成缺失清单
- **误差控制**：数值计算采用双精度（float64），关键结果附带误差估计

**异常处理与人工介入机制**：

| 异常场景 | 处理策略 |
|---------|---------|
| 型值表数据不完整 | Naval Arch Agent 生成缺失数据清单，状态进入 WAITING_USER，提示用户补充 |
| 计算参数超出经验范围 | 仿真引擎发出 Warning（非致命），结果中标注异常项，建议人工复核 |
| 外部求解器调用超时 | 自动重试 1 次，仍失败则降级为内置简化算法，结果中标注方法变更 |
| LLM 生成结果质量低 | PM Agent 检测到输出不符合预期 Schema 时，触发 Review Agent 复查修正 |
| 用户中途取消 | 清理进行中的子任务，保留已完成中间结果，用户可选择继续或放弃 |
| 整个 DAG 执行失败 | 保留所有中间结果和日志，PM Agent 生成失败分析报告，通知用户并提供重试选项 |

```

热插拔实现：
1. 工具开发者实现 BaseTool 接口
2. 提交 ToolManifest 到注册中心
3. 系统自动校验接口兼容性
4. 校验通过 → REGISTERED → 健康检查通过 → ONLINE
5. 工具实例独立部署在容器中，通过 gRPC 与主系统通信

│ 工程师        │ 项目内读写权限：知识库查阅、工具调用、          │
│ Engineer     │ 报告生成；不可管理成员                        │
├──────────────┼──────────────────────────────────────────┤
│ 访客          │ 指定项目只读：查阅报告、查看图纸；              │
│ Guest        │ 不可调用工具和导出                           │
├──────────────┼──────────────────────────────────────────┤
│ API 用户      │ 按申请范围授权：密钥认证，可限制调用频次和工具范围  │
│ API User     │                                          │
└──────────────┴──────────────────────────────────────────┘

权限粒度：
  ├── 项目级隔离：用户只能访问被授权项目的资源
  ├── 知识库级：按知识库模块独立授权（规范库、设计库、学术库...）
  ├── 工具级：敏感工具（如 CAD 操作、PDF 导出）需额外授权
  └── 数据级：型值表、计算报告等敏感数据可按字段级脱敏
```

**实现方案**：

- **认证**：JWT（Access Token 30min + Refresh Token 7d）+ OAuth2.0 集成
- **鉴权**：Casbin（支持 RBAC/ABAC，Go/Python SDK）
- **API Key**：HMAC-SHA256 签名，用于第三方 API 接入

### 7.2 数据安全

| 安全措施 | 实现方式 | 适用范围 |
|---------|---------|---------|
| **传输加密** | TLS 1.3，全站 HTTPS | 所有外部通信 |
| **内部通信加密** | mTLS（服务网格）或 gRPC TLS | 微服务间通信 |
| **密码存储** | bcrypt + salt | 用户密码 |
| **敏感信息脱敏** | 日志中自动脱敏（手机号、邮箱、API Key） | 日志系统 |
| **文件访问控制** | 预签名 URL（MinIO），有效期 15min | 图纸/报告下载 |
| **SQL 注入防护** | ORM（SQLAlchemy）+ 参数化查询 | 数据库操作 |
| **XSS/CSRF** | CSP Header + CSRF Token + 输入输出编码 | Web 前端 |

### 7.3 知识库访问控制

**项目隔离模型**：

```
项目 → 知识库模块 → 文件 的层级授权链：
═══════════════════════════════════════════════════

  Project A                 Project B
  ┌─────────────────┐      ┌─────────────────┐
  │ 项目知识库 A     │      │ 项目知识库 B     │
  │ (项目成员可见)   │      │ (项目成员可见)   │
  │                 │      │                 │
  │ 共享规范库 ◄────┼──────┼───────────────► │
  │ (CCS/IMO等)    │      │ (组织级共享)     │
  │                 │      │                 │
  │ 设计案例库       │      │ 设计案例库       │
  │ (项目私有)      │      │ (项目私有)       │
  └─────────────────┘      └─────────────────┘

  授权检查流程：
  1. 用户请求访问知识库文件
  2. 检查用户是否属于文件所属项目
  3. 检查文件所在模块的可见性（项目私有 / 组织共享 / 公开）
  4. 检查用户角色的读写权限
  5. 记录访问日志（谁、何时、访问了什么、做了什么操作）
```

### 7.4 合规审查记录

**合规要求对齐**：

| 合规要求 | 实现措施 |
|---------|---------|
| **《数据安全法》** | 数据分类分级存储，重要数据不出境，数据操作全量审计日志 |
| **《个人信息保护法》** | 最小必要原则收集信息，用户可查询/删除/导出个人数据 |
| **船舶行业保密** | 项目级数据隔离，文件加密存储（AES-256），图纸水印，导出审批 |
| **模型使用合规** | 记录每次 LLM 调用的输入输出摘要，保留 90 天，支持回溯审计 |
| **知识产权保护** | 知识库文件原始来源记录，生成内容标注 AI 生成标识 |

**审计日志保留策略**：

| 日志类型 | 保留时长 | 存储 |
|---------|---------|------|
| 用户操作日志 | 1 年 | TimescaleDB（30 天后压缩，90 天后归档 MinIO） |
| LLM 调用记录 | 90 天 | MongoDB → 定期归档 |
| 安全事件日志 | 3 年 | 不可变存储（MinIO WORM 模式） |
| 系统运行日志 | 30 天 | Loki + 定期清理 |
